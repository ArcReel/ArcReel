# API 状态与错误文案

仅在撰写、翻译或审阅 API 文档、状态标签、错误码和接口提示时读取本文件。

## 基本原则

- 先确认状态在当前接口中的真实含义，再选择中文。
- 不把一个英文状态词固定映射成唯一中文。
- 保持 HTTP 状态、业务状态、任务状态和界面提示之间的区别。
- 错误文案尽量说明问题、影响和恢复方式。
- 不修改状态码、枚举值、字段名和响应原文。

## 常见状态词

- `Success`
  - 根据语义使用 `已完成`、`已处理`、`请求成功`
- `Invalid`
  - 使用 `无效`、`格式有误`、`校验未通过`
  - 不默认翻译成 `非法`
- `Available`
  - 使用 `已开通`、`可获取`、`可访问`、`可使用`
- `Unsupported`
  - 使用 `暂不支持`、`不支持该类型`、`当前不支持`
- `Pending`
  - 使用 `待处理`、`处理中`、`待确认`
- `Expired`
  - 使用 `已过期`
- `Missing`
  - 使用 `缺少`、`未提供`
- `Denied`
  - 使用 `被拒绝`、`未通过`
- `Forbidden`
  - 根据语义使用 `无权限访问`、`当前不允许访问`
- `Not Found`
  - 使用 `未找到对应内容`、`未找到对应数据`
- `Accepted`
  - 使用 `已受理`、`已接收，等待处理`
- `Completed`
  - 使用 `已完成`
- `Failed`
  - 使用 `失败`、`处理失败`
- `Conflict`
  - 使用 `状态冲突`、`资源状态不一致`、`请求与当前状态冲突`
- `Unauthorized`
  - 根据实际原因使用 `未登录`、`认证未通过`、`缺少认证信息`
  - 不机械翻译成 `未授权`
- `Bad Request`
  - 使用 `请求参数有误`、`请求格式有误`
- `Timeout`
  - 使用 `请求超时`、`处理超时`

## 参数说明

每个参数尽量写清：

- 类型和格式
- 是否必填
- 单位
- 默认值
- 允许值或范围
- 缺省行为
- 与其他参数的依赖或互斥关系

不要用「正常值」「根据情况填写」「相关信息」等无法执行的说明。

## 错误文案结构

优先按以下顺序提供信息：

1. 发生了什么
2. 哪个对象受到影响
3. 可能原因
4. 可以执行的恢复操作
5. 仍然失败时需要提供的诊断信息

不要把推测写成确定原因，也不要在没有依据时承诺恢复时间。
