# 评估点之后:趋势评估与处置阶梯

账本轮数达到评估点后,每批新 actionable 处置前读本文。轮数**恰等于**评估点时先做「趋势评估」并汇报委派方,汇报后不等待,直接按「处置阶梯」处置本批;之后各批只走阶梯。

reviewer 每轮都会提出建议,这是其默认行为,不是代码仍有问题的证据。评估点之后,一条意见要被实施,须先说明它修复的具体问题。SKILL.md「暂停询问委派方」的三类(reviewer 冲突、业务取舍、故障)优先于本文:命中即暂停,不进阶梯、不受严重度门槛影响。

## 趋势评估

证据三处:`round.sh show` 的账本(每轮实施 / pushback 与归类)、`query.sh history` 的评论历史、`classify_commits.sh` 查看最近两批改了什么(commit 说明笼统时按 `sha` 执行 `git show` 查看改动本身;`SINCE_SHA` 告警按脚本 header 处置)。把前几轮与本批意见按语义归并为主题,统计每个主题跨越的轮数;连续两轮的改动都既未改善用户可感知的行为、也未降低后续改动成本,是后两类结论的典型证据。给出**一个**结论:

- **仍有真问题**:本批至少一条指向可复现的错误路径或用户可感知的行为缺陷,且不是重提
- **主要为防御性与风格**:本批以新增检查、兜底、默认值、命名、风格为主,无具体触发路径
- **reviewer 往复**:本批多数是已驳回意见以不同表述重提,或两家 reviewer 的偏好相互冲突

汇报固定五行,发给委派方:

1. 账本摘要:N 轮,累计实施 a / pushback b,各轮一句话归类
2. 结论:三类之一
3. 方向:本批哪类实施、哪类驳回
4. 仍开放条目数
5. 下一步:继续至第 M 轮(硬停)或建议合并

## 处置阶梯

对本批每条意见逐级判断,停在第一个成立的判据:

1. **重提在案 pushback** → 回复引用原 pushback 驳回;该主题写进汇报,正常退出时列入复盘的 ADR 候选
2. **无具体触发路径** → 驳回。意见要防的失败路径须能指出一个具体调用方或输入;回复评论写明追溯到的调用方与结论
3. **不降低后续改动成本** → 驳回。改动既不修复真实错误路径,也不消除重复、拆除错误抽象或删除不可达分支
4. **其余实施**:同根因合并为一处改动,整批一次 push

阶梯减少的是实施量,不减少核实:驳回前先追溯到调用方,证据写进回复。

**严重度门槛**:阶梯只对 CodeRabbit `potential_issue` / `major`、Gemini `high` / `critical`、Codex P0 / P1、code scanning 的全部评论,以及没有级别标签的 review body finding(CodeRabbit outside-diff、Codex `has_body_finding`)展开;其余级别逐条以统一说明回复驳回(写明自第 N 轮起只处理上述级别)。

**始终实施**,不走阶梯 1~3:信任边界的输入校验、防止数据丢失的错误处理、安全告警(或按 reviewers.md「已知误报」流程留痕)、委派方明确要求的改动。

## 硬停汇报

沿用上述五行,并附:仍开放条目清单(id、一句话、建议处置)、retrospective.md 规定的硬停产出。委派方据此裁决 merge、延长预算接力或转呈。
