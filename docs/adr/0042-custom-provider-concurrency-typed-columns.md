# Store custom-provider concurrency limits in typed, lane-named columns, not JSON / KV / child tables

Built-in provider concurrency limits already use `image_max_workers` / `video_max_workers` / `audio_max_workers` configuration keys in `provider_credential` / `ProviderConfig`, loaded by `CapacityTable.from_db` and projected by lane into the capacity table. Custom providers (the `custom_provider` table, runtime IDs shaped as `custom-{id}`) previously always received global defaults in `from_db`, preventing users from limiting individual custom providers' concurrency, unlike built-in providers.

Add **typed, lane-named columns to `custom_provider`**: `image_max_workers` / `video_max_workers` / `audio_max_workers` (nullable Integer), with `NULL` meaning "unset → use global default." When loading custom providers, `CapacityTable.from_db` reads each column and falls back to the global default for `NULL` (replacing the unconditional global-default behavior). Projection still uses `_lane_limits`, reusing the semantics established by the three-level fallback slice. Custom providers are outside the built-in `PROVIDER_REGISTRY` and have no intermediate "provider-declared default" layer, so their fallback has two levels (user column value → global default), instead of the built-ins' three. **Explicitly rejected**: ① a generic JSON `extra` column (requiring per-field read-modify-write and validation pipelines, complicating concurrent single-field read-modify-write; already disfavored in ADR 0016 and unjustified for three scalar limits here); ② a KV configuration table (custom-provider configuration does not belong to `ProviderConfig`'s preset-provider KV system; reuse would require resolver exceptions and bypass this table's single source of truth); ③ a concurrency-field child table (introducing a table + join for three scalar limits, with the most mechanical work).

This is a YAGNI tradeoff: only integer limits for three fixed lanes are currently needed; the field set is stable and symmetric with built-in providers. Typed columns are direct, indexable, and simplest to migrate, matching ADR 0037 (typed columns for multiple built-in provider secrets): "prefer typed columns when the field set is known and stable; reserve JSON / child tables for genuinely dynamic scenarios."

## Consequences

- **Explicitly accept sparse columns**: all three columns remain `NULL` for custom providers without configured concurrency (most rows). This ADR and `from_db`'s two-level-fallback comment explain them; they are not dead fields awaiting cleanup.
- **Refactoring trigger**: reassess moving to a JSON `extra` column or concurrency-field child table when custom providers need per-model concurrency, or lanes change from three fixed dimensions to dynamic extensibility. That would be evidence-based refactoring, and this ADR becomes superseded.
- **Bounded changes**: model + one additive nullable-column migration (no backfill; none of the three columns enters any `WHERE`), passthrough in `CustomProviderRepository.create_provider` / `update_provider`, CRUD schemas (POST / PUT request bodies + response echoes), custom-provider wiring in `CapacityTable.from_db`, and three nullable number inputs in the settings form. Do not change SlotTable's occupancy ledger, lane isolation, or reload mechanisms; do not introduce per-model concurrency.
- **Preserve existing boundaries**: build on the three-level-fallback slice (custom providers are its two-level special case) and ADR 0037 (typed columns for stable field sets). Any subsequent PR proposing JSON / KV / child tables must first deprecate this ADR.
