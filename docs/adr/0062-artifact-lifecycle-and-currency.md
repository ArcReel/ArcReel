# 产物生命周期以产物清单为唯一口径：补录即 current，stale 仍可用

用户为每一件产物（资产设计图、step1 中间稿、正式脚本、宫格图、分镜图、视频、旁白音频、字幕、演示物）付过一次费，系统必须能回答两个问题：它在不在，它是不是还对得上当前内容。靠扫目录或读脚本里的路径串只能答第一问，且把「文件在」误当「内容对得上」；靠为每件产物存一个状态字段则要求每次内容变更都同步回写，一处漏写就长期说谎。决定把答案收在**产物清单**（`lib/artifact_manifest.py`，项目目录内的 `.arcreel_artifacts.json` sidecar）：清单只登记每件正式产物的身份、落盘路径与**生成依据摘要**（basis digest，对该产物直接消费的正式内容与直接上游产物做 canonical JSON + sha256），**不存状态**；时效在读取时由当前项目投影出的期望依据与清单条目比对得出，四态 `current / stale / missing / blocked` 就此产生（`ArtifactStatus`）。状态不落盘，因此没有「忘记回写」这种失真形态——内容变了，下一次读取自然就报 stale。

## 决定

- **时效只追踪正式内容与直接上游产物。** basis 收的是产物的内容依据：正式脚本收 step1 与项目正式元数据，分镜图收脚本条目正文与它引用的资产 sheet / 原图，视频收分镜图与 unit 正文，依此类推。视觉产物（宫格图、分镜图、视频）的 basis 只描述正式内容：供应商与凭证、模型、像素分辨率、seed、音轨开关、prompt 渲染器版本一律**不进 basis**（`lib/visual_artifact_provenance.py`）——它们是「下一次怎么生成」的意图，改配置不该把用户手里已有的一屋子画面集体判旧、逼出一轮重复付费；配置变更由用户显式发起的下一次生成生效。旁白音频落在这条界线的另一侧：发声参数（供应商、模型、音色、语速）决定用户听到的是谁在念、念得多快，属于交付内容本身而非生成意图，因而与旁白正文一同进 basis（`lib/narration_delivery.py`），换音色后旧音频判 stale 是如实陈述。分界线是「这一位是否改变用户拿到的成品内容」，不是「它填在配置页还是写在脚本里」。
- **补录即 current。** 项目 schema 升到产物清单时，一次性把项目内既有正式产物按迁移那一刻投影出的依据登记进清单，登记值与期望值同源，因此补录完成的产物**一律判 current**。补录以 `project.json`、剧集剧本条目的 `generated_assets`、资产定义与受控的 `grids/grid_*.json` 记录为权威索引（`lib/artifact_activation.py`），不扫目录、不猜路径。不引入「legacy / 来历不明」第三态，也不因为「这件产物是旧流程生成的」而预设 stale：用户升级后不该被误导去重生一遍已经付过费的东西。产物文件不在、或补录当下依据无法从项目现状投影出来（如所需上游产物本身尚未存在）的目标不登记，读取时因清单无此条目而报 missing；归档导入走同一入口，但沿用归档里冻结的依据摘要而非当前投影，因此导入项目可能带 stale 条目——这是如实转述归档时的事实，不是缺陷。这与下文运行期的 `blocked` 是两回事：这里是补录当下压根没有条目可登记，`blocked` 说的是清单已有条目、但运行期读取或依据计算本身失败。
- **stale 仍可用。** `stale` 的语义是「比当前内容旧」而不是「不可用」：它可查看、照常参与成片与导出、不阻断任何步骤，也不是重生指令。可用集合 `usable = current ∪ stale`；不指定 ID 的生成调用只补 `missing`（缺失补齐），重做 stale 必须由用户显式选择。`blocked`（清单读不出、路径被 blocker 拦、依据不可用）一律 fail loud，不降级成 missing——把读不出来当作没有，会把一次故障变成一次自动付费。
- **任务结果与产物时效独立。** 一次批量生成按本次请求穷尽为 `succeeded ∪ failed ∪ blocked`（`GenerationItemState`），产物则独立报告四态，两组状态互不推导。强制重生一件 current 产物失败时，任务是 failed 而产物仍是 current；一件产物是 missing 也不意味着上一次任务失败过（可能从未请求）。回执同时并列两者，让调用方分别读，而不是二选一地把「这次没做成」和「现在没有可用内容」互相顶替。
- **四条状态轴不合并。** 产物时效（`ArtifactStatus`）、任务状态（队列行状态与对外的 `GenerationTaskState`）、批量准入结论（`BatchAdmissionDecision`，见 `docs/adr/0061`）、逐 ID 执行结果（`GenerationItemState`，`lib/generation_result.py`）回答的是四个不同问题——「现在有没有可用内容」「那个异步作业到哪一步了」「这批请求该不该发生」「已经发生的每一项下场如何」。它们在同一条回执记录上并列携带，不折叠成一个「状态」字段：任何一次折叠都要在别处补一张翻译表，且必然在某个组合上说错话（典型如任务成功但产物随后被外部删除、或产物 current 而本次强制重生失败）。
- **`schema_version == 8` 是唯一激活门。** 清单对一个项目是否生效，只看 `project.json` 的 `schema_version` 是否等于 `CURRENT_PROJECT_SCHEMA_VERSION`（`lib/project_schema.py`）。激活走前向提交：迁移在项目元数据锁内先做完整只读预检，再把整份清单一次写入；预检复核在此之后失败会把清单回滚到写入前的快照。清单写入之后才提交 schema 版本——这一步失败会让清单停在已写入的新内容、但 schema 仍是旧版本，因此清单不生效，等效于停在旧版本；不做清单层面的二次回滚，修复数据后重跑迁移即可收敛到新版本，重跑本身是幂等的整份重投影。`active_artifact_currency_resolver()` 对未激活项目返回 `None`，调用方按此退回历史读取行为——这一退回只发生在读路径，不构成生成许可：生成入口与 `enqueue_task()` 各自独立校验 schema 是否为当前版本，迁移（含补录）失败或尚未轮到迁移都一律拒绝生成，原因原样透出、项目只读可看，修复数据后重试。一个项目在任意时刻，关于「能不能生成」只有一个答案；关于「产物在不在、对不对得上」，激活后由清单口径回答，未激活时退回历史读取行为，两者不会同时生效。
- **清单锁协议是项目级、跨进程、全量替换。** 每个项目一把 `.artifact_manifest.lock`（portalocker 独占、非阻塞轮询、超时后报错而非无限等），粒度到项目而非剧集——产物依赖跨集共享资产 sheet，剧集级锁挡不住真正的竞争。所有写入都在同一把锁内完成 read-modify-write，落盘走临时文件 + fsync + 原子 rename，因此清单永远是一份自洽快照，不存在半写状态。作用域 CAS（只替换本次涉及的条目、保留无关条目）与全量 CAS 用于把「读—判—写」之间的漂移变成显式失败而不是覆盖。激活与付费前复核另需更粗的项目元数据锁 `.project.json.lock`，层级固定为元数据锁 ⊃ 清单锁，不反向嵌套。

## 明确不采用

- **扫目录或读脚本里的路径串判断产物存在**：只能答「文件在不在」，答不了「对不对得上当前内容」；且同一件事在前端、REST、智能体三侧各写一遍统计，删掉一张分镜后各处结论必然分叉。
- **在清单条目上存一个状态字段**：要求每一次内容写入都同步回写全部下游条目，漏一处就长期说谎，且回写本身要跨文件事务。读时比对把正确性建在「依据摘要相等」这一条不变式上，代价只是一次投影。
- **把生成配置一律纳入依据**：换一个视频模型就让全项目视频变 stale，等于用配置变更制造重复付费的暗示；只影响「下一次怎么生成」的配置该在下一次生成时生效，不追溯评判已有产物。反过来「凡填在配置页的一律不进 basis」同样不采用——旁白发声参数就填在配置页，却决定成品听感，按是否改变成品内容划线，不按填写位置划线。
- **补录后标 stale，或引入「未知来历」第三态**：升级本身不改变任何内容，凭空判旧只会把用户推去重生已付费的产物；第三态还要求每个消费方多写一条分支。
- **stale 自动重生**：「旧」不等于「该重做」。自动重生把一次状态查询变成一次扣费，且用户往往正是知道它旧、但这一版够用。
- **迁移失败后静默扮成一切正常**：迁移（含补录）失败不采用「吞掉错误、继续用历史读取行为回答产物状态」——那会让用户以为项目完好。失败须持久化为阻断性裁决（`migration verdict`，见 `CONTEXT.md`「迁移失败判定 / 需要修复」），原因原样透出、生成入口拒绝，读仍可读但不伪装成清单口径已生效。这与「尚未轮到迁移的项目走历史读取行为」不是一回事：后者没有失败过，不构成需要修复。
- **剧集级锁或逐条增量写清单**：激活写的是完整目标态，逐条写在中断后会留下半激活项目；跨集共享的资产 sheet 也让剧集级锁挡不住真正的并发写。

## Consequences

- **清单体量契约**：清单每次读写都是全量 parse / 全量序列化 + 整文件 rename，条目数上界约为 `资产数 + Σ_每集(2 + 宫格数 + 7 × 分镜条目数)`——每个剧本条目最多拥有分镜图、视频、音频、两种字幕与两种演示物共 7 个产物身份。百集 × 每集数十分镜的项目会到万级条目、单文件数 MB，单次读写成本随之线性上升。**这是本设计已知且接受的成本点**：条目不设上限、不做 LRU / TTL 裁剪——裁剪会让「产物在不在」重新变成猜测。清单只在两种情况下缩小：产物的 canonical 归属消失或移动（脚本条目被删、资源被改名），以及条目清空时整份 sidecar 被删除；**依据变化只让条目变 stale，不构成无主，故意保留**。若量级成为实际瓶颈，出路是分片或改用可增量读的容器，不是丢条目。
- 补录（迁移）失败会把整个项目置于阻断态：可读、可看已有产物、不可生成。这把「静默降级」换成了「显式停机 + 修复路径」，代价是一次数据异常会让用户完全无法继续生成，因此失败原因必须原样可见、且必须存在无需手改 JSON 的重试入口。
- 清单锁超时后报错而非排队，长时间持锁的写操作（激活、批量注册）会让并发的状态查询直接失败而不是拖住请求；状态查询本身在从未写过清单的项目上走 guarded 无锁双读，避免把只读查询变成一次写。
- 时效判定的正确性依赖「投影期望依据」与「登记依据」用同一份代码，两者一旦分叉会表现为整类产物无故 stale。新增产物种类时，登记路径与比对路径必须共用同一个 basis 构造器，不允许各写一份。
- 产品资产的标准化 sheet 与其余资产 sheet 共用这一套生命周期——登记为产物、按同一规则判四态、stale 可用不自动重生（见 `docs/adr/0034`）。
- 术语口径以 `CONTEXT.md`「产物与制作状态」一节为准：产物、Artifact Manifest（产物清单）、产物时效与四态、补录、任务结果与产物时效独立、制作状态、生成结果契约、缺失补齐等词条与本 ADR 同源，措辞不各自演化。
