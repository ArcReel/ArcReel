# 产物生命周期以产物清单为唯一口径：补录即 current，stale 仍可用

> 本 ADR 中「补录当下依据无法从项目现状投影出来的目标不登记、读取时报 missing」与「补录失败会把整个项目置于阻断态」的适用范围已由 `docs/adr/0098` 收窄：生成缺口不再阻止依据投影，文件可用的正式产物一律补录，只有依据确实算不出的不登记；因数据拒绝整个项目只限项目或剧本读不出与导入包不安全，迁移没能做完仍按本 ADR 阻断。

用户为每一件产物（资产设计图、script_plan 中间稿、正式脚本、宫格图、分镜图、视频、旁白音频、字幕、演示物）付过一次费，系统必须能回答两个问题：它在不在，它是不是还对得上当前内容。靠扫目录或读脚本里的路径串只能答第一问，且把「文件在」误当「内容对得上」；靠为每件产物存一个状态字段则要求每次内容变更都同步回写，一处漏写就长期说谎。决定把答案收在**产物清单**（`lib/artifacts/artifact_manifest.py`，项目目录内的 `.arcreel_artifacts.json` sidecar）：清单登记每件正式产物的身份、落盘路径与**生成依据摘要**（basis digest，对该产物直接消费的正式内容与直接上游产物做 canonical JSON + sha256），视频与音频还记下正式文件自身的内容事实（见下文），**不存状态**；时效在读取时由当前项目投影出的期望依据与清单条目比对得出，四态 `current / stale / missing / blocked` 就此产生（`ArtifactStatus`）。状态不落盘，因此没有「忘记回写」这种失真形态——内容变了，下一次读取自然就报 stale。

## 决定

- **时效只追踪正式内容与直接上游产物。** basis 收的是产物的内容依据：正式脚本收 script_plan 与项目正式元数据，分镜图收脚本条目正文与它引用的资产 sheet / 原图，视频收分镜图与 unit 正文，依此类推。视觉产物（宫格图、分镜图、视频）的 basis 只描述正式内容：供应商与凭证、模型、像素分辨率、seed、音轨开关、prompt 渲染器版本一律**不进 basis**（`lib/artifacts/visual_artifact_provenance.py`）——它们是「下一次怎么生成」的意图，改配置不该把用户手里已有的一屋子画面集体判旧、逼出一轮重复付费；配置变更由用户显式发起的下一次生成生效。旁白音频落在这条界线的另一侧：发声参数（供应商、模型、音色、语速）决定用户听到的是谁在念、念得多快，属于交付内容本身而非生成意图，因而与旁白正文一同进 basis（`lib/speech/narration_delivery.py`），换音色后旧音频判 stale 是如实陈述。分界线是「这一位是否改变用户拿到的成品内容」，不是「它填在配置页还是写在脚本里」。
- **作为成品带入的资产图按图本身登记。** 资产图的依据由描述、画风与原图推出，衍生资产图的依据由本体资产图与变化描述推出，这只对在本项目里生成出来的图成立；作者上传的资产图、从全局资产库应用到项目的资产图与随之带入的衍生资产图本身就是成品——不论它最初是在别的项目里生成的还是直接上传进库的，对项目有意义的是图本身，描述只是生成的输入，不参与对它的判定。库资产因此不带来源标记。上传与应用都在写入图的同一次正式提交里选中一条 `source: manual_upload` 版本记录（应用一批资产时，全部图的版本记录、文件、`project.json` 与清单登记同一次提交，任一步失败整体回滚）；规划器为资产图或衍生资产图投影期望依据时，若选中版本是手动上传、且其受管快照与声明的图字节一致，就投影一个只由图字节决定的依据（`build_uploaded_asset_sheet_basis`，不含描述、画风、本体资产图与资产名），否则照常按生成输入投影。登记不另算依据，而是经同一个规划器投影后登记，写入与比对同源。由此：描述为空时带入即被认领；之后改描述、改画风、改名都不让它变 stale，带入的衍生资产图也不随本体资产图重生成或本体描述变化而变 stale；之后在项目里生成并选中新的图，或图被外部替换得与选中快照字节不一致，都回到按生成输入判时效；还原到手动上传的版本则重新按图本身登记。没有上传记录的存量资产图维持按生成输入投影，不做追溯判别。版本记录由此成为资产图期望依据的输入：`versions.json` 读不出时，资产图时效与 typed media 一样判 blocked，不降级为按生成输入投影——否则成品图会被静默改判。只导出当前内容的归档随包保留选中的手动上传快照，导入与补录因此得出同一结论。
- **内容摘要按文件 stat 标识缓存，摘要值仍是内容哈希。** 投影期望依据要对资产设计图、分镜图等输入文件取内容摘要（`lib/infra/content_digest.py`），认领、请求、轮询会反复询问同一批文件。摘要以文件的 `(st_dev, st_ino, st_size, st_mtime_ns)` 为键缓存在进程内，容量有上限，满了按最久未用淘汰：标识不变就复用，标识变了就重新哈希。缓存的是内容哈希而不是标识，所以时效的判定语义不变：内容被替换，标识随之改变，下一次读取重新哈希并判 stale；复制、导入、恢复只改 mtime，会重算一次，内容相同则摘要相同，不会误判 stale。已知并接受的代价是，内容被替换、同时大小与纳秒 mtime 都被刻意还原成原值时，会返回旧摘要。刚写入的文件（mtime 距读完不足数秒）不入缓存，免得粗粒度时间戳下的连续改写被当作没变。缓存只在进程内，不落盘、不是第二套口径，丢掉它只损失速度。
- **写时记事实，读时算结论。** 写入时只记录不会因后续变更而失真的事实：生成依据，以及视频与音频产物自身的内容指纹。时效这类结论一律在读取时推导，不在写入时标记。项目文件有绕过接口的写入途径（Agent 直接编辑剧本、用户手动替换文件、导入与恢复），写时标记的正确性要靠每一个写入方都不出错；内容改回去之后还要撤销已经打上的标记；标记到一半中断，会留下错误的状态。读取时推导没有这些问题。读取慢的根源在读取的实现方式（逐件 IO、重复判定、重读视频），不在读取时推导这条原则本身。
- **视频与音频产物在写入时记录自身的内容事实。** 视频（`episode-video`）与旁白音频（`episode-audio`）的条目除路径与依据摘要外，还记下登记那一刻正式文件的内容指纹（裸 sha256 hexdigest）、字节数与纳秒 mtime（`ArtifactContentFacts`，清单里的 `content_digest` / `content_size` / `content_mtime_ns`）。版本记录同时记下该版本快照的内容指纹（`content_digest`）。采集集中在登记的公共入口（`observe_registered_artifact`）：付费生成、上传、恢复版本、配音交付与修复登记都经这里，事实取自准入时同一个描述符读到的那一版文件。激活（迁移激活与无信封归档的自证补录）证明「正式文件与选中版本快照字节一致」成立时，记下同一描述符的内容事实；v17→v18 迁移按同一条证明为存量视频与音频补录，同时写进清单条目与版本记录。带信封的归档导入，只有当激活证明成立、且证明的正是信封指纹那份字节时才带上内容事实；证明不成立的条目不带事实，导入后与源项目一样判 stale。改键与补偿回滚搬动或放回原条目，内容事实随条目保留。内容事实不参与条目相等：写入方 CAS、回滚判断与导入校验都只看路径与依据摘要。判断一次写入是否改变了清单时，内容事实计入比较。
- **判定视频与音频的时效时，对照登记的内容事实，不读版本快照。** 有内容事实才能证明正式文件就是登记的那个版本：字节数与纳秒 mtime 都与记录一致，就直接认定，不读文件内容；任一项不一致，才完整取指纹与记录比对，比对不一致时判 stale。登记的 mtime 不早于清单文件自身的 mtime 时，同一时间戳内的改写可能不改变任何一项 stat，按 racy 处理，退化为完整比对，做法与 git 以 index 文件为参照的 racy 判定同理。没有内容事实的条目无从证明，判 stale。版本快照只在真正被使用时校验：恢复版本、出成片前对照版本记录的指纹，不一致就失败并说明原因。成片依据里视频单元的内容指纹取版本记录的快照指纹，没有记录指纹的旧版本才现取。已知代价与内容摘要缓存一致：内容被替换、同时字节数与纳秒 mtime 都被刻意还原，就会漏判。
- **补录即 current。** 项目 schema 升到产物清单时，一次性把项目内既有正式产物按迁移那一刻投影出的依据登记进清单，登记值与期望值同源，因此补录完成的产物**一律判 current**。补录以 `project.json`、剧集剧本条目的 `generated_assets`、资产定义与受控的 `grids/grid_*.json` 记录为权威索引（`lib/artifacts/artifact_planner.py`，经 `lib/artifacts/artifact_activation.py` 这一统一门面对外），不扫目录、不猜路径。不引入「legacy / 来历不明」第三态，也不因为「这件产物是旧流程生成的」而预设 stale：用户升级后不该被误导去重生一遍已经付过费的东西。产物文件不在、或补录当下依据无法从项目现状投影出来（如所需上游产物本身尚未存在）的目标不登记，读取时因清单无此条目而报 missing；归档导入走同一入口，但沿用归档里冻结的依据摘要而非当前投影，因此导入项目可能带 stale 条目——这是如实转述归档时的事实，不是缺陷。字幕与演示物在物化时绑定当时选中的视频版本；单元之后换了选中视频（手动上传、AI 重新生成或切换版本），这些条目在导出与导入时暂不适用：对所依据的那个视频版本仍完整自证的照常保全，完整导出随包带上，导入后切回那个版本即重新成立；仅当前版本的导出不带旧版本快照，这些条目不随包。其他原因证明不了的条目照常让导出与导入失败。未激活项目仍可导出归档：导出是只读路径，对未激活（含迁移失败被阻断）的项目照常放行，其归档经数据版本闸判定不带清单信封（`server/services/project/project_archive.py`），导入端跑完迁移链后走自证补录，与升级路径同一口径。这条兼容分支故意保留——它与激活门同判据（schema 是否当前版本），判的是「当下有没有生效的清单可保全」：从未激活的项目如此；曾激活过、但 schema 落后于当前版本的项目亦然——清单文件虽在但已不生效，其冻结的依据摘要不进归档，导入端重投影后按补录口径重算，归档不为未生效的清单保留第二套读取口径。删掉这条分支等于让被阻断的项目连备份都导不出，把一次数据异常升级成数据被困。这与下文运行期的 `blocked` 是两回事：这里是补录当下压根没有条目可登记，`blocked` 说的是清单已有条目、但运行期读取或依据计算本身失败。
- **stale 仍可用。** `stale` 的语义是「比当前内容旧」而不是「不可用」：它可查看、照常参与成片与导出、不阻断任何步骤，也不是重生指令。可用集合 `usable = current ∪ stale`；不指定 ID 的生成调用只补 `missing`（缺失补齐），重做 stale 必须由用户显式选择。`blocked`（清单读不出、路径被 blocker 拦、依据不可用）一律 fail loud，不降级成 missing——把读不出来当作没有，会把一次故障变成一次自动付费。
- **任务结果与产物时效独立。** 一次批量生成按本次请求穷尽为 `succeeded ∪ failed ∪ blocked`（`GenerationItemState`），产物则独立报告四态，两组状态互不推导。强制重生一件 current 产物失败时，任务是 failed 而产物仍是 current；一件产物是 missing 也不意味着上一次任务失败过（可能从未请求）。回执同时并列两者，让调用方分别读，而不是二选一地把「这次没做成」和「现在没有可用内容」互相顶替。
- **四条状态轴不合并。** 产物时效（`ArtifactStatus`）、任务状态（队列行状态与对外的 `GenerationTaskState`）、批量准入结论（`BatchAdmissionDecision`，见 `docs/adr/0061`）、逐 ID 执行结果（`GenerationItemState`，`lib/generation/generation_result.py`）回答的是四个不同问题——「现在有没有可用内容」「那个异步作业到哪一步了」「这批请求该不该发生」「已经发生的每一项下场如何」。它们在同一条回执记录上并列携带，不折叠成一个「状态」字段：任何一次折叠都要在别处补一张翻译表，且必然在某个组合上说错话（典型如任务成功但产物随后被外部删除、或产物 current 而本次强制重生失败）。
- **`schema_version == 8` 是唯一激活门。** 清单对一个项目是否生效，只看 `project.json` 的 `schema_version` 是否等于 `CURRENT_PROJECT_SCHEMA_VERSION`（`lib/project/project_schema.py`）。激活走前向提交：迁移在项目元数据锁内先做完整只读预检，再把整份清单一次写入；预检复核在此之后失败会把清单回滚到写入前的快照。清单写入之后才提交 schema 版本——这一步失败会让清单停在已写入的新内容、但 schema 仍是旧版本，因此清单不生效，等效于停在旧版本；不做清单层面的二次回滚，修复数据后重跑迁移即可收敛到新版本，重跑本身是幂等的整份重投影。未激活项目没有第二套读取口径可退：`active_artifact_currency_resolver()` 对它直接抛 `ProjectMigrationError`，调用方拿不到 resolver 就无从回答产物状态，也就无从静默降级。阻断是统一的——生成入口、队列 `enqueue_task()`、MCP 工具与 REST 写入路径读同一条裁决（迁移失败的持久记录 ∪ schema 落后于当前版本），原因原样透出，修复数据后重试。阻断以入口声明为准：REST 写入路由挂 `require_project_migration_ok` 依赖、Agent 工具经工具声明的迁移阻断策略在入口包装；被调用方（如 `ScriptBatchEditor`）的内层裁决只作兜底，不作为某个入口省略声明的理由。重跑迁移链不是重对账入口：它对已是当前版本的项目直接返回、什么也不做；需要整份重投影时走 schema 保持的激活（`activate_artifact_target_state(bump_schema=False)`）——重算目标态并原子替换整份清单，条目无变化时返回 `False`，幂等可重入。日常的产物内容变化不需要重投影，由读取时的时效判定回答。项目仍可打开：只读路径按路径直取剧本与画布文件，不经清单。一个项目在任意时刻，关于「能不能生成」只有一个答案；关于「产物在不在、对不对得上」也只有一个答案——激活后由清单回答，未激活时是「读不出，先修复」。
- **清单锁协议是项目级、跨进程、全量替换。** 每个项目一把 `.artifact_manifest.lock`（portalocker 独占、非阻塞轮询、超时后报错而非无限等），粒度到项目而非剧集——产物依赖跨集共享资产 sheet，剧集级锁挡不住真正的竞争。所有写入都在同一把锁内完成 read-modify-write，落盘走临时文件 + fsync + 原子 rename，因此清单永远是一份自洽快照，不存在半写状态。读取因此不拿清单锁：读取方打开的描述符读到的必然是某一份完整清单；每次读取照常校验项目根身份、拒绝符号链接与 junction、拒绝 FIFO，只在进程内缓存解析结果。一次请求只读一份清单快照（时新性判定器构造时读入），请求内的准入与所有时效比对都在这份快照上进行，请求中途清单被替换不影响这次请求的结论。Windows 上读取方打开着清单时，原子替换与删除空清单都会因共享冲突失败，写入方此时短暂、有限次重试，重试耗尽后照常报错。作用域 CAS（只替换本次涉及的条目、保留无关条目）与全量 CAS 用于把「读—判—写」之间的漂移变成显式失败而不是覆盖。激活与付费前复核另需更粗的项目元数据锁 `.project.json.lock`，层级固定为元数据锁 ⊃ 清单锁，不反向嵌套。「超时后报错而非无限等」只描述清单锁；项目元数据锁（`lib/artifacts/formal_write.py`）是无超时的阻塞锁，按排队等待语义工作，两把锁的等待策略不作统一。

## 明确不采用

- **扫目录或读脚本里的路径串判断产物存在**：只能答「文件在不在」，答不了「对不对得上当前内容」；且同一件事在前端、REST、Agent 三侧各写一遍统计，删掉一张分镜后各处结论必然分叉。这条对未激活项目同样成立——为它们保留一套按文件存在性作答的旁路，等于把已被否掉的口径按 schema 分支留了一份。
- **在清单条目上存一个状态字段，或在写入时标记下游过时**：要求每一次内容写入都同步回写全部下游条目，漏一处就长期说谎，且回写本身要跨文件事务；绕过接口的写入、内容改回与中断的理由见上文「写时记事实，读时算结论」。读时比对把正确性建在「依据摘要相等」这一条不变式上，代价是每次读取都要做一次投影，其中最贵的是对输入文件取内容哈希；这部分按文件 stat 标识缓存，成本只取决于真正变化的文件，不随读取次数线性增长。
- **把生成配置一律纳入依据**：换一个视频模型就让全项目视频变 stale，等于用配置变更制造重复付费的暗示；只影响「下一次怎么生成」的配置该在下一次生成时生效，不追溯评判已有产物。反过来「凡填在配置页的一律不进 basis」同样不采用——旁白发声参数就填在配置页，却决定成品听感，按是否改变成品内容划线，不按填写位置划线。
- **补录后标 stale，或引入「未知来历」第三态**：升级本身不改变任何内容，凭空判旧只会把用户推去重生已付费的产物；第三态还要求每个消费方多写一条分支。
- **stale 自动重生**：「旧」不等于「该重做」。自动重生把一次状态查询变成一次扣费，且用户往往正是知道它旧、但这一版够用。
- **迁移失败后静默扮成一切正常**：迁移（含补录）失败不采用「吞掉错误、继续用历史读取行为回答产物状态」——那会让用户以为项目完好。失败须持久化为阻断性裁决（`migration verdict`，见 `GLOSSARY.md`「迁移失败判定」），原因原样透出、生成入口拒绝，项目仍可打开但不伪装成清单口径已生效。schema 落后、迁移链还没跑到的项目归在同一条裁决下：它没有写下的失败记录，可它同样一件产物都读不出，按 schema 判据现算出「尚未升级」即可，写下的记录优先只因为它点名了要修的具体数据。
- **剧集级锁或逐条增量写清单**：激活写的是完整目标态，逐条写在中断后会留下半激活项目；跨集共享的资产 sheet 也让剧集级锁挡不住真正的并发写。

## Consequences

- **清单体量契约**：清单每次写入都是全量 parse / 全量序列化 + 整文件 rename；只读查询按清单文件身份在进程内复用同一版本的解析结果，文件一变即整份重读重解析。条目数上界约为 `资产数 + Σ_每集(2 + 宫格数 + 7 × 分镜条目数)`——每个剧本条目最多拥有分镜图、视频、音频、两种字幕与两种演示物共 7 个产物身份。百集 × 每集数十分镜的项目会到万级条目、单文件数 MB，单次读写成本随之线性上升。**这是本设计已知且接受的成本点**：条目不设上限、不做 LRU / TTL 裁剪——裁剪会让「产物在不在」重新变成猜测。清单只在两种情况下缩小：产物的 canonical 归属消失或移动（脚本条目被删、资源被改名），以及条目清空时整份 sidecar 被删除；**依据变化只让条目变 stale，不构成无主，故意保留**。若量级成为实际瓶颈，出路是分片或改用可增量读的容器，不是丢条目。
- 补录（迁移）失败会把整个项目置于阻断态：可读、可看已有产物、不可生成。这把「静默降级」换成了「显式停机 + 修复路径」，代价是一次数据异常会让用户完全无法继续生成，因此失败原因必须原样可见、且必须存在无需手改 JSON 的重试入口。
- 读取不拿清单锁，长时间持锁的写操作（激活、批量注册）不会让并发的状态查询等待或失败；清单锁超时报错只落在并发的写入方。读取也不创建锁文件，只读查询不会变成一次写。
- 时效判定的正确性依赖「投影期望依据」与「登记依据」用同一份代码，两者一旦分叉会表现为整类产物无故 stale。新增产物种类时，登记路径与比对路径必须共用同一个 basis 构造器，不允许各写一份。
- 产品资产的标准化 sheet 与其余资产 sheet 共用这一套生命周期——登记为产物、按同一规则判四态、stale 可用不自动重生（见 `docs/adr/0034`）。
- `lib.artifacts.artifact_activation` 的统一门面是长期契约：按职责拆分出的 `artifact_planner` / `artifact_currency` / `artifact_input_claims` / `artifact_registration` 四个子模块不对模块外直接暴露，外部引用一律经门面命名空间；底层数据模块 `lib.artifacts.artifact_manifest` 不属此拆分，不受本条约束。测试打桩是设计内例外：门面按 re-export 提供符号，patch 门面别名替换不了子模块内部的运行时引用，因而替换子模块行为的打桩落在实现模块上。若将来要让拆分对消费方可见，须先修订本条并迁移调用点。
- 术语口径以 `GLOSSARY.md`「产物与制作状态」一节为准：产物、产物清单、产物时效、补录、制作状态等词条与本 ADR 同源，措辞不各自演化；本 ADR 独有的机制陈述（四条状态轴不合并、缺失补齐、任务结果与产物时效独立）只在此处记录，术语表不复述。

## 用户提供的产物（修订）

「作为成品带入的资产图按图本身登记」推广到用户上传的分镜图与视频：选中版本是与产物字节一致的用户上传时，期望依据只由上传字节决定，提示词、引用资产、画风与分镜图上游都不参与。由此上传即 current，之后改提示词、改资产都不让它变 stale，下游消费它时（视频以分镜图为输入）不再追问生成依据；生成并选中新版本，或分镜图被外部替换得与选中快照不一致、视频被外部替换得与登记的内容指纹不一致，则回到按生成输入判时效。系统不判断用户上传的内容与当前脚本是否相符，这一判断留给创作者。

此前上传视频一律不登记、只凭版本记录的手动上传兜底认领，上传分镜图在提示词为空或引用资产缺资产图时被删去条目、判 missing 并使下游视频以「分镜图未登记」被拒，两种做法一并废止；按缺失补齐的批量生成因此不会再付费覆盖用户上传的产物。

## 分镜图与宫格的依据不记资产名（修订）

「按是否改变成品内容划线」同样适用于资产名：分镜图、宫格联合图与切格分镜发给图像模型的参考图只按类型列「图N」，正文 `@[名称]` 也渲染成「图N」，资产名不是模型输入。这三类依据因此只记资产参考图的类型、角色、种类与内容指纹，提示词里指认资产参考图的 mention 换成「图N」，对不上参考图的 mention 原样保留（模型看到的就是名字）；上一分镜图等非资产参考图的身份照记（`lib/artifacts/visual_artifact_provenance.py` 的 `without_asset_names`）。资产只改名时这些产物保持 current，换了资产图才变 stale。参考生视频的声明行与分镜图生视频的台词含资产名，资产图的提示词含资产名，它们的依据照记，改名后变 stale 是正确的。

宫格与切格分镜的依据按宫格记录冻结的参考图重放，资产改名的级联事务因此连带改写宫格记录里的参考图名字与随改名迁移的路径。存量项目由 v18→v19 平移：清单只改写升级前时新的登记，版本记录冻结的依据按同一函数逐条改写，依据格式变化不让存量产物整体过期。
