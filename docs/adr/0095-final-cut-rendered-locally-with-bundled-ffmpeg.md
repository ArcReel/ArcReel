# 成片在本地渲染车道上用随包 ffmpeg 渲染，成片与剪映草稿落盘登记为产物

成片由服务端以子进程调用 ffmpeg filtergraph 渲染：入出点裁切、转场、混音、字幕烧录在一张滤镜图里完成，按硬切边界分段渲染后无损拼接，内存随每段片段数而不是整集长度增长。渲染成片与导出剪映草稿都是生成队列里的任务，走一条不绑定供应商的本地车道 `render`，全局并发固定为 1、不开放配置：单段渲染的峰值内存以 GB 计，并发一高就会撑爆 Docker 容器。它们不调用供应商，因此不写用量记录（`docs/adr/0076`）。

**成片固定使用 `imageio-ffmpeg` 随包分发的 ffmpeg，不看系统 PATH，也不提供路径配置。** 受支持的部署形态是 Docker 镜像与 Windows、macOS 直接运行，`imageio-ffmpeg` 的 wheel 对这三者都自带含 libx264、libass 与 xfade 的静态构建。系统里的 ffmpeg 能力参差：Homebrew 默认构建没有 libass，烧不了字幕；Windows 上通常根本没装。固定用随包的那一个，所有环境渲染出的成片一致，不需要能力挑选与逐项降级。仓库里其他调用 ffmpeg 的地方（如缩略图）经同一个查找器取用它；它不带 ffprobe，媒体探测另行处理。字幕字体同样随仓库自带一款 OFL 许可的中文字体（单一粗体字重），渲染时经 `fontsdir` 指给 libass，不依赖系统字体。

**成片与剪映草稿落盘在项目目录内，并登记进产物清单。** 产物身份是「集 + 剪辑时间线 + 旁白版本」（`docs/adr/0089`、`docs/adr/0090`）。生成依据在任务开始时按指定修订取快照；先渲染到项目内的临时文件，验收通过后原子替换正式文件，再用这份依据登记，因此渲染期间剪辑时间线被改动时，产物一出来就如实判为 stale。剪映草稿落盘时，草稿内的素材路径写成占位符，用户本机的草稿目录与剪映版本这类只影响落到用户机器上的形态的参数，在下载打包时才代入，不进产物身份与生成依据。每个产物身份只保留最新文件，版本号照常递增；项目归档不包含成片与剪映草稿，导入后判 missing，重新渲染即可。

## 明确不采用

- **按「显式配置 → PATH → 随包二进制」查找并按能力挑选**：为几乎不存在的需求（自选更新版本、硬件编码）引入能力探测与不一致的出片结果。
- **缺什么能力就逐项降级**（没有 libass 用 Pillow 叠字幕、没有 xfade 退化为硬切）：成片会静默地与剪映草稿不一致，违背两者同源。
- **MoviePy、MLT、GES、Remotion 与浏览器端渲染**：分别因依赖冲突与性能、无法经 pip 安装、许可证与按次计费、编码能力与性能而排除。
- **成片按供应商车道调度或并发可配**：没有供应商可挂靠，而内存峰值决定了并发只能是 1。
- **剪映草稿维持现场生成、下载即删**：无法判定时效，也不符合产物的定义。
- **保留成片的历史版本文件**：成片由剪辑时间线修订与素材在本地重新渲染即可得到，不花钱，体积却以百 MB 计；视频单元的视频是付费生成的，才保留全部版本。

## Consequences

- `imageio-ffmpeg` 停在 FFmpeg 7.x，且 2025-01 之后没有发新版；需要更换时只改查找器一处。随包 ffmpeg 与字体都是再分发，发布时附上对应的许可证声明与源码获取方式。
- 渲染前，剪辑时间线的检查结果里有阻断级问题即拒绝；带旁白版本还要求每段旁白都有可用的旁白配音（current 或 stale）。渲染后检查音视频流与时长偏差，结果随任务结果返回。
- 转场不改变总时长（`docs/adr/0090`）：重叠型转场从前一剪辑片段出点之后、后一剪辑片段入点之前各借半个转场时长的源素材，余量不足时用定格帧补齐；非重叠型（闪黑、闪白）只在切点两侧各做半程淡出与淡入。剪映端的实际表现需实测，逐项不一致的转场从词表剔除。
