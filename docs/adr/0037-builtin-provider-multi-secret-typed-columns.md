# Store multi-secret built-in provider credentials in typed registry-key-named columns, not JSON / child tables / concatenation

Kling is the first built-in provider requiring **two secret strings** (`access_key` + `secret_key`, JWT HS256 authentication). `docs/adr/0008` already established that "multi-field credentials use only built-in providers' `PROVIDER_REGISTRY.required_keys: list[str]`," but that is only the **declaration layer**. Built-in-provider credential **storage** is the `provider_credential` table (`docs/adr/0016`'s multiple credentials + manual active selection), with fixed `api_key` / `credentials_path` / `base_url` columns. `overlay_config()` copies only those columns, leaving no room for a second secret. Existing "multi-field" providers do not actually have two secret strings: gemini-vertex uses one service-account file path (the `credentials_path` column); all others have a single `api_key`.

Add **typed columns named by registry keys to `provider_credential`** (`access_key`, `secret_key`, nullable Text). `overlay_config()` emits config using column names unchanged (`config["access_key"] = ...`), maintaining **registry key name = form field name = backend constructor parameter name = config dict key** throughout, without a column-name↔key translation layer; reuse `mask_secret` per column for redaction. **Explicitly rejected**: ① concatenating `access_key:secret_key` into one `api_key` and splitting later (already rejected by `docs/adr/0008`, breaking `mask_secret`'s single-key display semantics); ② a generic JSON `extra` column (`docs/adr/0016` already rejects "complex concurrent read-modify-write for one JSON field," and per-field redaction pipelines would be needed); ③ a credential-field child table (a table + join for one provider, with the most mechanical work); ④ reusing KV `ProviderConfig` for Kling secrets (bypassing `docs/adr/0016`: no participation in active multi-credential switching, invisible to readiness checks, requiring resolver exceptions).

This is a YAGNI tradeoff: only Kling currently needs two secret strings (Volcengine visual CV AKSK is not a built-in provider in this batch; Vertex uses one file path). A JSON/child-table mechanism for one provider is not worthwhile; typed columns also continue the existing precedent of "provider-specific typed columns" such as `credentials_path`.

## Consequences

- **Explicitly accept column-growth risk**: `provider_credential`'s `access_key`/`secret_key` are always NULL for every provider except Kling (sparse columns); synonymous `api_key` and `access_key` columns coexist. This ADR and registry declarations explain them; they are not dead fields awaiting cleanup.
- **Refactoring trigger**: when a **third** built-in provider needs ≥2 secret fields (especially with differing field names), reassess moving to a generic JSON `extra` column or credential-field child table. That would be evidence-based refactoring, and this ADR becomes superseded.
- **Preserve existing boundaries**: build on `docs/adr/0008` (no concatenation bypass; multi-field credentials only through built-in providers) and `docs/adr/0016` (dedicated credential table + typed columns, without JSON). Subsequent PRs proposing JSON/child tables/concatenation must first deprecate this ADR.
- **Bound changes to the credential layer**: model + one additive nullable-column migration (no backfill; neither column enters any `WHERE`), `CredentialRepository.create/update`, `overlay_config`, credential CRUD routes (request bodies + per-field-redacted responses + field metadata), and settings-page credential forms (rendered by `required_keys`). Provider-specific connectivity tests (such as Kling JWT-signed probes) are outside this layer and accompany each provider integration.
