# Custom-provider credentials stay `api_key` + `base_url`; multi-field credential protocols use built-in providers only

ArcReel's `CustomProvider` ORM (`lib/db/models/custom_provider.py`) currently exposes only two credential fields per user-created runtime provider: `api_key` (one string masked by `mask_secret`) + `base_url` (HTTP entry point). Concurrent video-API adaptation research found several native multi-field protocols: official Kling uses JWT HS256 (`access_key` + `secret_key`, 30-minute token expiry); Vertex AI Veo uses service-account JSON files (`credentials_path`, plus project_id / OAuth2 scopes); Volcengine visual.volcengineapi.com visual CV uses AKSK + canonical requests + HMAC signatures. Exposing these unchanged as custom-provider endpoints would require multi-field credentials (candidates: `extra_credentials: JSON`, or dedicated `api_secret` / `service_account_json` fields).

**Do not expand custom-provider credentials.** `CustomProvider` remains one `api_key` field + `base_url` long-term. Native multi-field protocols integrate **only** through built-in providers (`PROVIDER_REGISTRY.required_keys: list[str]`, already supporting multiple fields, such as `gemini-vertex.required_keys=["credentials_path"]`; Kling uses `credential_groups=[["api_key"], ["access_key","secret_key"]]` to choose single-key Bearer or dual-key JWT). Users accessing multi-field protocols through intermediaries rely on **intermediary protocol translation**: intermediaries handle multi-field authentication server-side and expose Bearer `api_key` + intermediary `base_url` (evidence: Kling intermediaries commonly forward native schemas at `/kling/v1/videos/{text2video|image2video|multi-image2video}`, collapsing authentication to one Bearer key). Endpoint closures always see one api_key. This is the boundary decoupling credential models from protocol shapes.

## Consequences

- **Protocol shapes do not contaminate credentials**: introduce no multi-field exceptions into CustomProvider schemas, repositories, `mask_secret`, encrypted storage, UI credential forms (settings "add custom provider"), or `/api/v1/custom-providers/discover`. Adding native multi-field protocols (Kling, Vertex, AKSK, future providers) does not touch this chain. Protocol extension points consolidate in backend implementations under `lib/backends/video_backends/`, `lib/backends/image_backends/`, `lib/backends/text_backends/` and `ENDPOINT_REGISTRY` registration, leaving credentials stable.
- **One backend may support two credential modes**: `KlingVideoBackend` (`lib/backends/video_backends/kling.py`, `auth_mode="jwt"|"bearer"`) selects by credential shape. Built-in `kling` uses JWT (`KlingJWTManager`) for `access_key + secret_key`, Bearer for `api_key`, preferring api_key when both exist (`_build_kling` in `lib/backends/backend_assembly/specs.py`). `kling-video` endpoint closures accept only `api_key + base_url`, always Bearer. Both share request-body schemas/state mappings. This matches `GeminiVideoBackend`'s existing `backend_type=aistudio|vertex` modes (`lib/backends/video_backends/gemini.py`): backends carry protocol shapes, with authentication as constructor parameters.
- **Nonproxyable protocols never appear in endpoint dropdowns**: Vertex AI Veo (service-account files cannot redirect through base_url to intermediaries), Volcengine visual CV (SigV4-like signatures are usually repackaged as NewAPI forwarding rather than forwarded unchanged), etc. remain absent from custom-provider UI. This conscious tradeoff directs genuine needs to built-in providers.
- **Future plugins preserve the constraint**: runtime plugin endpoints likewise accept only `api_key` + `base_url`. Multi-field plugin protocols need their own built-in-provider-style declarations (effectively plugin-provided PROVIDER_REGISTRY extensions, considerably more complex and not presumed here), preserving stable plugin interfaces.
- **GLOSSARY.md already contains this principle** ("custom provider (自定义供应商)"). This ADR explains why credentials do not expand, complementing glossary "what is it" definitions. Subsequent exceptions (JSON credential fields, secondary keys) must first deprecate this ADR.
- **Do not bypass through delimiter-concatenated api_key strings** (such as manually splitting `api_key="access_key:secret_key"`). This breaks `mask_secret`'s single-secret display semantics, prevents UI identification of actual secret portions, and mixes string parsing into backends, blurring protocol structure versus credential representation. Genuine exceptions require new built-in providers, not endpoint-closure hacks.
- **Consistent with `docs/adr/0001-image-capability-resolved-at-execution.md`**: clarify runtime determination versus startup declaration. Providers declare credential shapes at registration (`PROVIDER_REGISTRY.required_keys`), without request-time dynamic expansion. Endpoints are constructed at runtime, but ENDPOINT_REGISTRY + CustomProvider schemas statically constrain credentials.
