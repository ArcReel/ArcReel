# project.json 文件级 schema 版本化 + 启动时逐级幂等迁移

不版本化、靠读时即时兼容旧字段虽零迁移成本，但旧形状字段会无限期残留、读路径分支越积越多。决定为 project.json 引入顶层 `schema_version` + `lib/project_migrations` 注册表，启动时扫各项目逐级跑纯函数 migrator（迁移前备份、原子写回、级联迁移剧本），单项目失败隔离不中断启动——显式版本化换取数据形状收敛与一次性改写，胜过读路径无限累积兼容分支。

## Consequences

- 引入备份 / 原子写 / 失败隔离 / 幂等机制复杂度，且迁移就地改写文件不可逆（如 v0→v1 拆 clue 为 scene/prop 并删 importance；v1→v2 归一化 provider）。
- 同一迁移链不只在启动期跑：项目归档**导入**路径也复用 `migrate_project_dir`，因为启动期 runner 只覆盖启动时已存在的项目，启动后导入的旧归档需在导入入口补跑完整链。
- 涉及多文件级联的迁移不能只依赖 `project.json` 的单文件原子写；schema v6 先在同父目录 staging 树完成资产名、剧本/草稿引用、媒体与版本历史改写，全部成功后再整目录替换，任一阶段失败保留原项目树。
- 目录替换是两次改名（原目录 → `.<项目名>.v6-rollback-<hex>`，staging 树 `.<项目名>.v6-<hex>` → 项目目录），窗口内进程被硬杀时项目目录不存在、rollback 目录残留——恢复责任归启动期扫描：runner 在遍历项目前认领 rollback 目录，对应项目目录缺失时原子改回并记录，项目在本轮继续迁移。
- 两类中间目录的名字由同一个模块生成与反解、后缀同构：名字是崩溃后唯一的线索，命名端与反解端分家会让认领与清理静默失效。
- 项目目录在位时 rollback 目录只是备份，与遗留 staging 树一并按版本化备份的年龄闸口清理；项目目录缺失期间不清理，它是唯一的项目数据。
- staging 树是整个项目目录的副本，因此 v5→v6 带一道按项目体量核磁盘容量的只读预检。迁移器的只读预检由 runner 在写下版本化备份之前跑，预检拒绝时项目目录一个字节都没被动过。
