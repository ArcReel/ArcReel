# 参考视频关键分镜预览与请求级图片模型选择

参考生视频的 Step 2 在正式视频生成前产出一组“关键分镜”：每个关键分镜代表同一 Video Unit 内一次核心场景切换后的静态第一帧。数量由文稿内容决定，不设固定模板；单个 Video Unit 最多 5 个。Step 1 同时给出关键分镜规划，若规划将超过 5 个，必须在该场景切换处继续拆分 Video Unit。普通资产引用与关键分镜引用共同受目标视频模型的参考图上限约束，采用二者中更严格的上限。

关键分镜使用稳定 ID（`E{episode}U{unit}K{index}`）和正文 tag `@[关键分镜 ID]`。正文仍决定参考图的使用位置和顺序；`keyframes[]` 只保存不能从正文机械派生的首帧描述与当前图片指针。它是 ADR-0064“正文唯一真相”的窄例外，不恢复旧的手工 `references[]`：删除关键分镜必须同步删除正文 tag，生成视频时依旧按正文中的首次提及顺序投影参考图。

Step 2 正式落盘后，系统以项目默认图片模型自动批量生成所有缺失的关键首帧。用户随后可在关键分镜卡片上编辑描述、生成/重生成、图片编辑、版本恢复、删除或新增关键场景。语义上哪些画面应成为关键分镜由生成模型提出并由用户验收；自动化测试只验证 ID、tag、顺序、上限和任务链路，不固化示例内容或固定数量。

所有图片写入口统一接受可选的请求级 `image_provider` + `image_model` 完整二元组，包括角色/场景/道具/商品资产、普通分镜图、Grid、关键分镜和 Image Edit。省略二元组时沿用项目默认图片模型；提供时只影响本次请求，不回写项目或全局设置。前端下拉显示配置目录中的 `provider/model`，默认项明确标为“使用项目默认模型”。

## Consequences

- Step 1/Step 2 schema、草稿晋升、Agent 直接生成与 Web CRUD 共用同一关键分镜结构。
- 关键分镜图片进入 VersionManager 的 `keyframes` 资源桶，但不伪装成 Artifact Manifest 正式资源；版本恢复只切换文件/版本指针。
- H3 投影可同时解析普通资产与关键分镜，按正文顺序提交，并在模型上限处收紧。
- 自动批量生成始终使用默认图片模型；只有用户主动生成、重生成或编辑时才采用下拉中的请求级覆盖。
