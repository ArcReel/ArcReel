# 保留核心库与服务端两个根，目录按领域术语表分包

后端代码分两个根：`lib/`（核心库）与 `server/`（服务端）。核心库顶层有 131 个 Python 文件，其中根 `__init__.py` 之外平铺着 130 个散模块；文件名前缀早已是事实上的子领域，应用服务层 `server/services/` 也有 30 个平铺模块，目录与领域术语表（`CONTEXT.md`）不同构，读完术语表仍不知道去哪里找代码。

我们决定**保留 `lib` 与 `server` 两个根且名字不变，服务端的外部启动入口不变；两个根之下按术语表分包**：核心库顶层只留包、不留散文件，一个模块归哪个包看它实现的是术语表哪一节的术语，文件名前缀只作初筛；包内再次出现前缀聚类就再拆（「脚本与分镜」一节因此是 `script` / `episode` / `prompts` 三个包），不设文件数上限，也不建 `common` / `utils` 一类的包，纯技术工具集中在命名明确的 `infra`。应用服务层按既有聚类建子包；其中不依赖服务端、也没有隐式耦合（模块级全局状态、会话生命周期、交付层契约）的纯领域模块移入核心库对应的包。分界的判据是「模块是什么」而不是「谁在用它」：只被服务端使用的领域模块仍属核心库。

每个模块的新归属写在 `scripts/regroup/module_map.toml`，它是这次归组的唯一真相源：搬迁脚本照表执行，预演脚本 `scripts/regroup/preview.py` 用它与现有导入图算出新包边界下的包间环、既有 import-linter 契约改写后的判定与镜像测试的去向。搬迁不留任何旧路径兼容层（不做 re-export），文件名默认不变、只换目录。

**明确不采用**：

- **按领域垂直切片**（每个领域一个目录，内含它的路由、Agent 工具、服务与核心逻辑）。同一个领域核心同时被 HTTP 路由、Agent 工具、远端 MCP 与生成 Worker 四类入口共用；切片会把 Agent 工具运行时（统一的工具注册、权限与会话上下文）打散到各领域目录，并让每个领域目录都依赖交付层，核心库「不知道 HTTP、Agent SDK、SSE 的存在」这条分界也就无从检验。
- **合并为单一根包**（例如 `arcreel/`，下挂 `core` 与 `server`）。收益只是名字更规范；代价是服务端的外部启动入口（容器镜像、本地开发命令与外部启动器都按 `server.app:app` 启动）全部要跟着改，而且合并本身不让目录更贴近术语表。
- **只给核心库改名**。`lib` 这个名字确实什么也没说，但换一个名字同样说不出它由哪些领域构成——表达领域的是它下面的包，不是根的名字；改名的代价与合并为单一根包相同。

## 包间环如实登记，不靠改名或拆文件消除

新包边界下，核心库顶层有 14 个包处于同一个强连通分量里。成因有二：当前代码里已经有一个 77 个模块的模块级环（项目管理器、产物清单一族、配置解析、自定义供应商与部分仓储互相可达），它横跨十个以上领域，任何按术语节的归属都拆不开；`project` 包同时持有被各领域引用的底层词汇（资产类型、资源路径、项目 schema 版本）与引用各领域的顶层编排者（项目管理器）。处置顺序是先调整归属、其次记为存量豁免；拆文件属于行为重构，不在归组范围。三处归属因此偏离了文件名前缀的直觉：任务类型桶归 `backends` 而不是 `config`（放进 `config` 会让分层契约的最底层直接依赖上层），参考图快照归 `artifacts`、图N 编号归 `prompts`（放进 `references` 会让参考图包传递依赖参考生视频子包，破坏路线中立约束）。其余包间环逐条登记在映射表的 `[accepted_edges]`，每条写明为什么不能靠调整归属消除。

## Consequences

- 读完术语表就能按章节找到包；新增模块时按「它实现哪一节的术语」落位，归属有争议时以映射表里的裁定为先例。
- 核心库的包之间不是分层的：包间环是存量，是否为包间方向立契约、何时立，按某个方向实际出问题时再针对性补，不为每个新包预先立契约。
- 下游分支在搬迁合入后运行同一个搬迁脚本改写自己的新增代码；主干只发生这一次大规模路径变更。
- 文件名保留原样，部分路径因此带有与包名重复的前缀（如 `lib/artifacts/artifact_manifest.py`）。去掉前缀会让全仓的打桩路径与检索词再变一次，收益只是少几个字符，本次不做。
