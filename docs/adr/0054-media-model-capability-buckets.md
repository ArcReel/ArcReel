# 图片 / 视频模型按能力桶配置：单一默认 + 可选能力覆盖

部分视频模型只具备部分能力（仅 i2v、无参考图槽位），单一「视频模型」配置项表达不了这一约束，选错模型的项目要到参考生视频路径执行期才失败。决定图片与视频统一为「**单一默认模型 + 按 capability 的可选覆盖桶**」：图片 t2i / i2i、视频 i2v / r2v，解析顺序与文本档位（`docs/adr/0051`）同构、项目优先——项目桶 > 项目默认 > 全局桶 > 全局默认 > 自动推断，空桶回退默认层。桶与调用点的映射固定在代码里：图片按执行时请求形态归桶（见 `docs/adr/0001`），视频先按**项目生成路线**定轴——路线创建即定、之后不可变（读侧归桶函数 `lib/config/resolver.video_bucket_for_generation_mode`，路线谓词 `project_manager.is_reference_video_project`），剧本不承载路线信息，三种 content_mode 同一口径（见 `docs/adr/0055`）。分镜路线（含宫格装配）→ i2v；参考路线内再按镜头是否携带参考图分流：有参考图 → r2v，**无参考图的退化镜头降级 → i2v**（镜头级判据在 `lib/reference_video/units.py`：执行层按解析后的实际参考图判定，入队预检 / 限流投影 / 费用估算按 unit 声明的 references 近似）。图片两槽的配置形态由本 ADR 收敛，`docs/adr/0015` 的端点三拆与运行时 gating 不受影响。

## 明确不采用

- **t2v 桶**：唯一调用点是参考路线的无图退化镜头，该场景由 i2v 桶承接（降级执行）：i2v 桶已有配置面与解析闸，为纯文本场景单设第三桶徒增配置面。降级把退化镜头的成败判据从「r2v 桶模型是否收空参考」换成「i2v 桶模型是否收纯文本请求」，不承诺该镜头一定可执行——i2v 闸只校验 `first_frame`，只服务图生端点的型号（Vidu 的 `viduq3-pro-fast` / `viduq1-classic` / `vidu2.0` 不在 `/text2video` 白名单）收到空参考仍在执行期显式失败。落在这一残留面的是「只支持图生视频」的窄能力型号，比原先落在「拒空参考的 r2v 主流型号」（DashScope R2V、MiniMax S2V 抛 `video_reference_images_required`）窄得多，且换配 i2v 桶即可自解。
- **按生成路线逐路配置模型**：路线是视频来源路径不是能力，表达不了「模型只有部分能力」的原始约束，且路线增减会直接冲击配置面。
- **强制逐桶配置（无默认层）**：全能力模型是主流场景，逐桶强配对多数用户是纯负担，平铺的同构下拉也无主次可言；默认 + 按需细化在配置面上从紧。
- **能力不满足时静默换模型**：用户会在不知情下用未选过的模型付费。解析时能力校验失败直接结构化报错（对齐文本 vision 先例），错误信息指引配置对应桶。
- **桶引用的写入侧拦截与级联清理**：桶引用悬空的成因（自定义模型能力覆盖被修改、模型 / 供应商被删、endpoint 变更、注册表升级改系统判定）统一由解析闸报错兜底。写入侧拦截需反向扫描散落各 project.json 的项目桶，昂贵且有并发窗口；级联清理是另一种静默改配置。已入队任务按 payload 照常执行，不回头补校验。

## Consequences

- 能力真相源维持既有声明、不新增副本：两桶都取 backend `VideoCapabilities`——i2v 看 `first_frame`（分镜路线由首帧驱动，宫格装配不改变这一点），r2v 看 `max_reference_images > 0`；自定义供应商 = endpoint 系统判定 ⊕ 模型级 `capability_overrides` 合成。内置视频模型的这两维只在 backend 声明，registry `ModelInfo` 不带视频能力位与参考图上限——单一 token 无从区分图生与参考生两条路径（如 `happyhorse-1.0-r2v` 只接受参考图、不接受首帧）。桶下拉据此预过滤候选；默认层下拉不过滤——默认层不承诺任何能力。
- 全部读侧（`video_capabilities` 查询与 agent 工具、费用估算、时长 / 分辨率约束收窄）与执行侧同口径：按上述口径定桶后走同一解析函数。项目级读侧（`video_capabilities` 查询、ad 派生分组的时长上限、分镜文稿预览）按项目路线一次定轴、不需要剧集与剧本上下文，三种 content_mode 不分支——它们求值时 unit 尚不存在或与 unit 无关，没有可分流的镜头；镜头级读侧（费用估算、限流路由投影、逐 unit 的时长 / 分辨率约束收窄与默认时长）对参考路线读取剧本 unit 声明的参考集、逐镜头分桶（退化镜头按 i2v 桶模型），剧本 / unit 读不到时回退路线主桶 r2v。WebUI 的逐条视频生成端点同口径：入队预检与 `generation_tasks.execute_video_task` 都按项目路线定桶，参考路线项目在该入口直接被拒并指引改走参考生视频流程（见 `docs/adr/0055`）。路线创建即定不可变，能力查询结果因此在项目生命周期内不会换桶；参考路线项目内单个镜头的生效桶随其参考集编辑变化。
- 已入队任务的执行身份在入队时锁定：解析出的 `provider/model` 以桶键形态（`video_provider_<cap>`）写进 task payload，执行与中断续跑都按它执行。task 行只存 provider_id 时 model 会按彼时配置重解析（自定义供应商更是补不出默认 model 而整段 payload 优先级落空），排队期间改配置即等于换模型——与「不静默换模型」相悖。锁定的身份仍校验存在性：供应商已下线、模型被删或禁用、endpoint 改成其它媒体类型时报错，既不回退 payload 旧键、也不回退项目 / 全局配置——换身份续跑会拿另一个 backend 去轮原身份的 `provider_job_id`。校验止于存在性，不重跑能力闸：闸在入队时已过，已入队任务按 payload 照常执行。参考路线的入队定桶按 unit 声明近似、执行按解析后的实际参考图定桶，二者分裂时（ad 声明了参考但资产全缺图）入队锁定的桶键会指向不会执行的身份——执行层在向 provider 提交前把锁定键与 `provider_id` 投影列改写为实际执行身份，续跑因此始终跟随实际执行过的 backend。自定义供应商的身份还含 endpoint 维度——它决定协议、是 backend 构造的真正输入粒度，而模型行的 endpoint 可在同媒体类型内改写（换中转商 / 换协议），`provider/model` 不变也会换掉 backend：提交拿到 `provider_job_id` 时一并持久化当时的 endpoint，续跑接续轮询前比对模型行当下的 endpoint，不一致即显式失败，不拿新协议 backend 轮旧协议下创建的 job。拦截只针对已提交、持有 job id 的续跑；排队未提交的任务照常按新 endpoint 提交。
- 图片侧空桶语义是「回退默认层」，不存在「空 = 跟随自动推断」的读法；存量配置的键组合在迁移中穷举处置。
- 前端呈现与 per-model 存储按**执行模型**取键：凡按模型查能力或按模型存配置的界面元素（能力面板、`model_settings` 下的分辨率等），一律取当前配置真正会执行的模型——细分桶生效时是桶内模型，否则是默认层穿透演算的结果；视频侧先按项目路线定桶再求值，与后端按路线定桶的口径同源，项目内全集一致。图片侧一类例外：`executingImageModel` 只取 T2I 层的执行模型，图片分辨率据此存取键，I2I 走独立的执行模型——两者配置不同模型时，I2I 执行期按自己的模型查 `model_settings` 查不到该键，回落供应商默认分辨率档位。默认层模型不作查询或存储的键，除非它就是执行模型。
- 设置 UI 三媒体（文本档位 / 图片桶 / 视频桶）共用同一交互形态：默认主下拉常驻 + 折叠的能力细分区，未配置桶的占位穿透演算到最终生效模型并标注各桶覆盖的调用点（zh / en / vi 同步）；创建向导只暴露默认层。
