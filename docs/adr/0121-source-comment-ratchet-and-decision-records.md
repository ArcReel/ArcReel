# 源码注释逐步减少，长期决策写入 ADR

源码与配置中的注释容易随实现漂移，应优先用命名、类型和测试表达意图。难以逆转、仅读代码无法推断且有真实取舍的决策，写入对应主题的 ADR。清理过时注释时，若发现实现依赖带已知缺陷的权宜做法，将影响与验收条件写入议题。

`ARC001` 以 Git 基线为准，按同一文件路径比较每种注释原文的出现次数。存量注释可以删除，同文件内移动位置时可保留原文。新增、改写、复制或移到其他文件的注释会被 lint 拦截。基线随合并前移，已删除的注释在后续改动中恢复时同样会报错。这样既支持分批合入清理，也避免靠删除一条旧注释来换取别处的新增额度。

解释器声明、类型与工具指令、许可声明，以及项目测试读取的 `@enqueue` 等标记仍由对应工具消费。工具豁免及其必填理由可以保留，由原闸门校验。例如，Knip 的 `@public` 同行需要写明导出为何要保留。Markdown 文档、生成的锁文件以及按 skill 锁文件维护的上游副本，各自按对应的流程处理。

用户直接复制或编辑的配置文件保留就地帮助注释。环境变量示例（`.env.example`）和两个 Compose 部署文件（`deploy/docker-compose.yml`、`deploy/production/docker-compose.yml`）可以用注释说明如何填写、何时改动以及改动后果。其他配置文件按源码规则检查。

提取器基于 Python 词法分析器和随开发依赖分发的语法解析器识别注释，避免将字符串中的注释符号误计为注释。运行时直接调用已安装的语法包，不从网络临时下载解析器。
