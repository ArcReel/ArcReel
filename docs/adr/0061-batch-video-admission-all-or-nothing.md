# 批量视频生成的准入是整批的，执行结果才是逐条的

「生成全部 / 批量生成」在创建任何任务之前，先把本次请求的目标集合作为一个整体评估一次：解析出稳定的目标集合，逐目标复用同一次 `SpeechComposition`、同一份旁白交付判定与同一份请求投影，任一目标存在重规划、混合发声、资产缺失、无法解析、TTS 问题、超出供应商上限、在途任务冲突或未确认的跨档费用，**整批创建零个任务**。只有全部目标通过，才在同一次准入操作里创建完整任务集合；顺序入队中途失败会撤销本次已创建的任务，不留半批。判定落在两层共享缝：`lib/batch_admission.py` 是传输无关的纯折叠（结论、确认分档、逐 unit 转述），`server/services/video_batch_admission.py` 把当前状态（任务库、TTS 在途、报价、请求投影）接上去；Web 批量端点与 Agent 的四个视频工具都走这一条，不各自实现一份。

**准入的原子性与执行结果的部分成败是两件事，不能互相顶替。** 入队前的问题是「这次请求该不该发生」——它由用户当前的剧本、资产与配置决定，逐条放行只会让用户为一批半成品付费，并把「另外几条为什么没排上」留给他自己拼。入队后的问题是「已经发生的执行怎么样了」——供应商侧的失败天然逐条独立，成败按 `requested / succeeded / failed / blocked` 契约逐 ID 报告（`lib/generation_result.py`）。受阻的整批同样用这套契约转述：每个目标都有自己的结论，本身没问题的目标带 `generation_batch_admission_withheld` 并指名是谁拦下的，调用方不必从「清单里没有它」反推。

## 明确不采用

- **逐条准入、逐条入队（前端串行循环）**：第一个坏目标之前的任务已经创建并计费，用户拿到的是一批半成品加一句失败提示；且判定分散在浏览器循环里，Agent 侧另有一份，两侧口径必然分叉。
- **首个异常即中断，只报第一个缺口**：批量场景下缺口常常同时存在多个，只报第一个会把一次操作变成 N 轮试错，每轮都要重新解析整份剧本。整批结论要求逐目标都带自己的稳定问题码、原因、当前/所需档位与下一步。
- **把整批拒绝塌成通用 4xx**：一次「评估成功、结论是不放行」不是请求错误。批量端点三种结局（放行 / 待确认 / 受阻）一律 200 返回同一信封，调用方按 `decision` 分支；HTTP 错误码留给真正的请求错误与入队中断。
- **确认时冻结执行内容快照**：确认绑定的是本次请求已解析的目标集合与选项（含按 unit 的申请档位），不冻结正文、引用、供应商或 TTS。worker 起跑时仍按最新意图重投影——冻结快照会让用户在确认后所做的修改被静默丢弃，且与执行期判据同源的原则相悖（见 `docs/adr/0056`）。
- **自动重生陈旧但可用的旧产物**：目标集合由用户选择或「缺失即生成」语义决定；把「旧」当作「该重做」会在用户没要求时重复计费。

## Consequences

- 替整批选定准入判据与时长基准的入口——Web 批量端点与 Agent 的四个视频工具——请求必须显式声明本次旁白交付方式，缺省与非法值一律拒绝、不创建任何任务：选「使用当前 TTS」时全部有旁白配音的目标都要有 fresh 且可测的 TTS，选「后期配音」则不因 TTS 未配置、缺失或过期受阻。单目标 REST 入口不在此列，它由用户在那一条的界面上直接触发、界面已呈现该条的旁白状态与费用，省略即沿用界面上的后期配音默认。
- 跨档费用的确认按申请档位聚合展示（每档的档位、unit 数、合计费用），报价不全的档位不显示合计——部分求和会低报用户正在同意支付的金额。
- 并发提交由两道护栏收口：准入前一次性探明全部目标的在途任务，重复提交命中队列的唯一索引去重并如实报告 `deduped`。
- 可入队性（能否构造 `TaskSpec`，见 `docs/adr/0001`）是目标集合的边界，先于准入判定：构造不出请求的 unit 带着自己的问题码进入结论，不被解析、不被报价，也不被静默丢弃。
