# 分集规划由服务端工具内文本模型分批滚动执行，drama 账本即分集大纲

> 本 ADR 中「审阅意见走重置 + 重新规划」与「窗口字数、每批集数上限 project settings 可覆盖」两条已由文末「重新规划走候选→采纳，窗口是内部常数（修订）」取代，其余内容仍然有效。

旧流程由主 agent 多步执行机械脚本（peek 阅读单位口径 → 换算字符口径 → 选锚点 → dry-run → split）：切分点零剧情语义留不住钩子，多步约定押在 agent 的流程遵循上，且逐集滚动使规划时看不到下一集内容。决定把拆分点判断交给 LLM、流程交给确定性工具：新增 plan 服务端 MCP 工具，内部读源文窗口（数万字级）调项目配置的文本模型，一次规划出窗口内所有剧情弧完整的集（标题/钩子/范围），cursor 只推进到最后一个高置信切分点、尾巴留给下一批；Pydantic schema 强约束，锚点存在性与范围连续性做机械校验、失败在工具层自动重试，重试附带上一轮校验失败原因（schema 错误/锚点不存在/范围不连续）引导针对性修正而非原样重发。主 agent 只调一次工具收摘要，不再承载切分过程。drama 模式账本条目加厚为分集大纲（故事节点、钩子、下集预告语 + 软素材范围），剧本生成的输入包含本集大纲与下集大纲；narration 账本保持薄（精确切分点 + 钩子）。审阅为批级：规划完成后展示账本摘要供用户确认，用户对已规划内容的调整意见走「重置 + 重新规划」——先用 `reset_episode_planning` 把账本退回到意见中最早受影响的集（保留其前的集不受影响），再带调整后的意见重新分批调用 plan；新提交的集号若与重置前的已消费范围重叠，提交时按磁盘下游产物探测自动标 stale（产物不删除）。

## Considered Options

- 规划 SubAgent（Claude 读窗口产账本）：多轮迭代能力在此用不上（钩子质量取决于 prompt 与全局视野），流程遵循靠 prompt、难单测，token 走 agent 凭证。
- 全本一次性规划：百万字级成本前置；用户常只做前几集试水，中途改风格后账本大面积作废。
- 逐集拆分（现状改良）：跨集节奏视野缺失，钩子质量天花板低，接续仍依赖滚动状态。
- drama 一步直出剧本：与分批规划冲突（一批几十集无法一次写完），调任何切分点都要重写整集剧本。

## Consequences

- `peek_split_point.py` / `split_episode.py` / `_text_utils.py` 删除，manage-project SKILL.md 切分章节与 CLAUDE.*.md 阶段 2 指令改写为单工具调用。
- v1 质量保障 = 全局窗口视野 + hook 字段显式化 + 批级审阅，不加 LLM judge 验证环。
- 规划质量依赖项目配置的文本模型能力，schema 与机械校验只兜形式正确性。
- 窗口字数、每批集数上限为工具内部默认，project settings 可覆盖。
- 账本的 hook 与下集预告进入剧本生成输入，并以集级元数据字段落入剧本 JSON（钩子设计落地到成片末场）；场次/景别/画外音等更重的剧本结构升级是独立项，不在本决策内。

## 重新规划走候选→采纳，窗口是内部常数（修订）

分集规划有两种做法：AI 规划，与手工切分（创作者在整本源文上划定集的边界、拖动相邻两集的边界，或在规划游标之后落刀切出新集）。两者切出的集同属「切自整本源文」，共用连续性、接续集号与 stale 标记规则。

对已有规划的调整是重新规划，面向创作者的动作里没有重置：

- 从第 N 集起重新规划时，AI 产出一份候选规划，分集账本不动；创作者看过候选的集与变更摘要（替换哪几集、新规划几集、哪些已有产物的集将标记 stale）后采纳，才在项目锁内一次性替换；放弃则什么都不变。采纳时校验账本自候选生成后未被改动，改动过则拒绝并提示重新生成。候选让调整始终可撤回：若先清空账本再规划，规划失败或结果更差时旧账本已不可恢复。
- 整本源文变更导致指纹不符时，沿游标接续规划与从第 N 集（N>1）起的重新规划都依赖旧坐标，一律拒绝；出路是从第 1 集起的重新规划。它不依赖旧坐标，按当前源文生成候选，旧账本在采纳前保持原样；采纳时整体替换全部切自整本源文的集，并重记 `source_fingerprints`。
- 首次规划与沿游标接续规划不覆盖任何内容，直接提交，不经候选。
- 同一项目同时至多一份候选；候选未决时不能发起新的规划。
- 重新规划范围内夹有自带原文或没有原文的集时拒绝执行，并点名这些集。
- `reset_episode_planning` 是底层服务命令；手工切分中「移除这一集之后的所有切分」经确认清单直接执行，不经候选。

窗口字数与每批集数上限不是创作者参数，Web、Agent 与项目设置都不能覆盖。窗口大小只影响调用次数与每批产出的集数，不影响切分质量（每批只提交剧情弧完整的集，尾巴留给下一批），也几乎不影响总读取量；约束来自模型的输出能力。窗口取 5 万字，作为每批读取原文的上限。每批集数上限由当前文本模型登记的输出上限推导：输出上限 × 安全系数 ÷ 每集输出估算。实测 drama 每集输出约 250–450 token；narration 没有故事节点与下集预告，约为其三分之一（未实测）。估算值与安全系数在实现时校准。模型没有登记输出上限时，按保守默认值推导。输出截断是 `docs/adr/0044` 的硬错误，意味着模型登记的输出上限不准，提示修正模型配置或换模型。模型输出上限的登记见 `docs/adr/0044` 修订。

「规划到源文结尾」由服务端逐窗串联，可随时停止，已提交的批次保留；「先规划一批」即一个窗口。创作者可见的体量参考只有项目的集目标时长（可选），它影响每集切多大，不影响窗口。

### Considered Options

- 重置与规划合成一步：破坏性，规划失败后旧账本不可恢复。
- 候选与现有规划按原文位置完整并排对比：采纳判断只需要候选的首尾句和变更代价，完整对比的交互成本留待原型评估。
- 按每集目标体量推导每批读多少原文：多一组需要实测校准的估算常数，而窗口大小对结果影响很小。
- 固定常数、截断即报错让创作者换模型：批次大小由系统决定，截断是系统一次要了超出模型能力的输出，把补救推给创作者不合理，很多创作者也换不了模型。
- 截断后自动缩批并在本次运行内记住：每次运行要浪费一次打满输出的调用，且掩盖了模型能力这一根因。
- 窗口覆盖只留给 Agent（project.json 顶层字段）：Web 用户碰到截断只能打开 Agent，两端能力不对等；旋钮挂在项目上，也对不准模型能力这一根因。
- 按模型上下文长度决定窗口：输入侧从不是约束，主流模型的上下文远大于窗口。
