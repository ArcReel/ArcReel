# Provider concurrency limits reject user-entered 0 (require ≥1 or blank); 0 remains only an internal unsupported-lane sentinel

`0` has two conflicting roles in the concurrency system: internally, CapacityTable uses lane capacity `0` as the "provider does not support this media" sentinel (`_lane_limits` projects unsupported lanes to `0` according to `media_types`; the worker's `if cap <= 0` immediately fast-fails with `mark_failed("provider_unsupported_media")`). User-configurable concurrency limits (built-ins through `_validate_value`, custom providers through API `ge=0` + DB `CHECK >= 0`), however, previously all **accepted** `0`. Entering `0` (misreading a "default" placeholder or assuming `0` means unlimited) silently disables the lane, after which every task reports "provider does not support this media": a silent trap with a misleading failure message. Registry factory defaults in `ProviderMeta.default_concurrency` already require `>= 1`; only user values allow `0`, creating asymmetry.

**Remove `0` from valid user input**: every user-input layer (frontend forms, custom-provider API `Field(ge=1)`, built-in `_validate_value`'s `parsed < 1`) and DB CHECK (the three `custom_provider` columns `>= 1`) uniformly require `>= 1`; blank / `NULL` still means "fall back to default." Keep `0` only as CapacityTable's internal "unsupported lane" sentinel, unavailable to users. Because custom-provider concurrency (ADR 0042) has not yet shipped, tighten DB CHECK by **directly rewriting its column-addition migration** (`>= 0` → `>= 1`, constraint names `_non_negative` → `_positive`), without a new migration or data backfill (`0` has no automatic source; its only source is user input, so blocking entry prevents further creation). Leave runtime `if cap <= 0` / `_lane_limits` / `provider_unsupported_media` unchanged: `0` can now arise only because "this provider does not support this media," making the failure-code semantics correct.

**Explicitly rejected**: making `0` a first-class "disable this lane" setting. Providers are bound at enqueue time; `0` cannot reroute tasks to another provider and only fast-fails, so it cannot "gracefully disable." The three-level fallback already expresses "use default" cleanly through blank / `NULL`, so `0` needs no second meaning. To avoid using a provider for a lane, do not select it for that lane. If "disable a provider's lane" becomes a real requirement, introduce an explicit switch with an accurate failure code instead of overloading `0`.

## Consequences

- **Separate the two `0` roles completely**: the user contract "concurrency limit is an integer ≥1 or blank" and the internal "capacity `0` = unsupported lane" no longer share a user-reachable value. Update `SlotTable`'s docstring to record the user-contract side.
- **Rewrite a migration already merged into main**: other concurrent worktrees / development databases that ran `alembic upgrade head` on the old (`>= 0`) version will not automatically receive tighter CHECK constraints (alembic does not rerun applied revisions). They need `downgrade -1 && upgrade head` or a rebuilt development database. With no release yet and no automatic source of `0`, this is harmless in practice: an intentional "unreleased migrations may be rewritten in place" tradeoff that must not be reused after release.
- **Bounded changes**: validation at three input layers + three DB-column CHECKs + in-place tightening of the original migration + i18n copy (backend `max_workers_must_be_positive_integer`, frontend "positive integer" and help text) + corresponding tests. Runtime scheduling, SlotTable, lane isolation, and reload remain unchanged.
- **Preserve boundaries**: align with the registry's `default_concurrency >= 1` rule; build on ADR 0042 (typed custom-provider concurrency columns).
