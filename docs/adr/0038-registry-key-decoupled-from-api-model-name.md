# Decouple dual-modality models with registry aliases and `api_model_name`, without composite `(model_id, media_type)` registry keys

`PROVIDER_REGISTRY[provider].models` uses model_id strings as unique keys, with one `ModelInfo` and one `media_type` per model_id. This key serves three roles: **UI / persistence identity** (frontend model pickers, `"model"` in `project.json`, the `ApiCall.model` column, and API request bodies all use this bare string), **billing / capability lookup key** (exact matching in `lib/billing/pricing/lookup.py` and capability lookups), and **model name sent to provider APIs**. Sharing one globally unique string for all three roles breaks for "dual-modality models": Kling v3-omni image and video APIs **both use `kling-v3-omni`**, but one key with one `media_type` cannot hold two modality entries for the same API name.

Add **`api_model_name: str | None = None` to `ModelInfo`** (default `None` falls back to the key, without affecting existing entries), separating "API name sent to providers" from "unique internal key." Use **alias key** `kling-v3-omni-image` for the image entry (`api_model_name="kling-v3-omni"`), reserving primary key `kling-v3-omni` for video. The image backend sends `api_model_name or 键名` (the video backend has no current alias requirement because the only dual-modality entry occupies the primary key and its key equals the API name, so it still sends the key directly). Billing and capability lookups continue using registry keys. Give the entries distinct `display_name` values (“可灵 V3-Omni（图像）” / “可灵 v3 Omni”), without exposing synthetic keys in the UI.

**Explicitly rejected**: changing registry keys to composite `(model_id, media_type)`. Composite keys fit reality better at the registry layer (one API model with two modalities = two rows sharing model_id, requiring neither alias keys nor `api_model_name`), but change model_id's two otherwise-working roles. model_id is a **cross-layer identity token**: frontend selection / `project.json` / `ApiCall.model` / API request bodies / pricing lookups all use **bare strings without accompanying `media_type`**. Composite keys push costs into all these boundaries. In particular, cost snapshots (`docs/adr/0009`) have only a model string at finish time, historical `ApiCall` rows cannot recover `media_type`, and pricing-module rate dicts also use model-string keys and would require composite keys. Dual modality conflicts only with model_id's "API name" role. Imposing composite keys across the whole system for that, with only one dual-modality model in the registry, is disproportionate. Principle: **decouple only the conflicting role; leave the two working roles intact.**

## Consequences

- **Backward compatibility**: existing models have `api_model_name=None` and fall back to keys with unchanged behavior; new single-modality models need not consider this field.
- **Asymmetric backend adaptation**: only image paths currently consume `api_model_name` (`KlingImageBackend` accepts it and uses it to send API names); video backends have no `api_model_name` parameter and send keys directly. This works today because the video entry of the sole dual-modality model, v3-omni, occupies the primary key equal to its API name. If a future dual-modality model needs its **video** entry to use an alias, video backends must first gain `api_model_name` support or send an incorrect key as API name. This is prerequisite work for the "refactoring trigger" below.
- **Explicitly accept synthetic-key awkwardness**: `kling-v3-omni-image` is an internal registry identifier absent from the provider's world, explained through this ADR and hidden by `display_name`; it is not a dead key awaiting cleanup.
- **Refactoring trigger**: when dual-modality models grow numerous and "alias key + `api_model_name`" boilerplate becomes burdensome, reassess composite `(model_id, media_type)` keys or other root solutions. That would be evidence-based refactoring, and this ADR becomes superseded.
- **Related consolidation**: build on `docs/adr/0009` (pricing joins `ModelInfo`, keyed lookups) and `docs/adr/0013` (model-level capability declarations), all answering "what do registry keys / `ModelInfo` carry?" This is the third responsibility separation for registry keys: separating "external API name" from "unique internal key."
