# 价目表用「计量项 × 选择维度」的通用结构，单币种不换算，查不到单价记为未定价

模型条目的价目表不再分成若干种定价形状，而是统一为一份结构：一个币种，加上若干计量项，每个计量项给出按选择维度取值的单价，可带单请求免费额度。计算器只遍历计量项求和，不按定价形状或媒体类型分派。费用 = 倍率 × Σ 计量项 max(用量 − 免费额度, 0) × 单价(选择维度)。主流厂商的计价都能落到这个公式上，而「按秒计价 + 参考图按张加价 + 按次基价」这类混合计价，用固定形态无法表达，只能拼接。

## 规则

- 请求级阶梯和服务档都按选择维度处理，不另设机制。上下文档按输入 token 总量（含缓存读写）落档，由计算器推算；服务档是普通选择维度，不建模乘数。
- 选择维度由代码定义，目录数据不能自创维度，因为调用方不提供取值的维度没有意义。价目表可以为维度声明默认取值，供请求没有指定取值时使用（例如分辨率为 Auto 时，取实际出片的分辨率）。
- 各计量项的用量互不重叠：未缓存输入、缓存读、5 分钟缓存写、1 小时缓存写四项之和等于总输入。各家 usage 的语义差异由调用侧在上报用量前处理，计算器不识别具体供应商。
- 计数规则是模型本身的事实：「字符数」计量项可以声明「汉字计 2」，由计算器按原始文本计数，backend 不自行计数。
- 每个条目只有一份价目表，币种取模型厂商主站的币种，不做汇率换算；用量统计按币种分别汇总。国际站用户需要另一个币种的价格时，可以修改条目。
- 渠道价差只用倍率表达，分两级相乘：供应商倍率是用户偏好，供应商模型倍率随官方同步下发，修改后关闭同步。倍率作用在整笔费用上，不按计量项分别设置。按订阅计费的内置供应商（`ark-agent-plan`）默认供应商倍率为 0。
- 查不到单价时记为未定价，与费用为 0 区分，不回落到其他模型的价格。以下三种情况都算查不到：条目未收录、条目没有价目表、单价表缺少请求的维度组合且没有默认取值。
- 价格只来自模型目录，供应商在响应中回报的实际消耗（如 Vidu 的 `credits`）不参与计算。
- 不建模：缓存存储费、按时段的闲时价、Batch、区域端点加价、预置吞吐、订阅、促销、违规费和版权附加费。ArcReel 当前不会触发的维度（Vidu 的错峰、百炼的思考模式）也暂不定义，以后需要时再新增选择维度，结构不变。

## Considered Options

- **合并为按 token、按张、按秒、按次、按字符 5 种固定形态**：表单简单，但混合计价要跨形态拼接，每遇到一种新组合都要改计算器。自定义模型的表单可以把这 5 种形态做成预设，由预设生成通用结构。
- **一个条目按站点带多份价目表**：百炼、MiniMax、可灵等厂商的国内站和国际站各有一套价格，两套价格之间不是汇率关系。但为少数国际站用户引入「供应商模型选用哪份价目表」的概念，代价过高；LiteLLM、new-api 也都只有一套价格。
- **统一为单一币种，在快照中按固定汇率折算**：方舟等只有人民币价的模型会带上汇率误差，而且汇率由谁维护、多久更新，又会变成新的同步问题。
- **查不到单价时回落到默认模型或最接近的档**：这是旧做法，算出的金额看起来正常，实际上是另一个模型或另一档的价格，比显示「未定价」更容易误导用户。
- **优先采用供应商回报的实际消耗**：Vidu 的 `credits` 能反映促销，但只有内置渠道才会返回，倍率也无法统一生效。参考费用的定位不需要这份精度。

## Consequences

- `PricingKind` 的 10 种形状、`_calculate_custom_cost` 按 call_type 硬算的逻辑，以及 `lookup_pricing` 的回落链都将移除。`price_unit` 不再有独立语义，自定义模型现有价格字段的迁移在迁移方案中决定。
- `api_calls.cost_amount` 需要可以为空，用来表示未定价。使用记录要单独显示未定价调用。
