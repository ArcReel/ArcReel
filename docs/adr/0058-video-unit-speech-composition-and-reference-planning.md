# 视频生成单元统一发声归属，广告参考路线采用自包含单元

ArcReel 的三种内容模式与两种生成路线形成了六种组合，它们分别演化了声音语义：同一创作单元可以同时含人物发声与叙述旁白；有的路径把两者都交给视频供应商，有的过滤旁白但没有 TTS，有的保留供应商原音后再叠加独立旁白。广告参考路线还以 `shots` 为内容真相、`reference_units` 为派生分组，费用、入队、执行与导出分别水合，单元边界和产物来源因此容易漂移。

用户对生成的稳定心智是「一个视频生成单元 = 一次视频请求 = 一次计费 = 一条片段」。声音归属、时长确认、请求身份与产物失效都应围绕这个单元收敛，而不是由各内容模式、路由和执行器分别决定。

## 决定

- **视频生成单元是计费与产物边界**：分镜路线由说书片段、剧集场景或广告镜头承载；参考路线统一由自包含 `video_units` 承载。参考单元内的 shot 只是时间编排，不是独立请求或产物单位。
- **一个单元只有一个发声归属**：人物对白、人物内心独白和人物画外解说都属于人物发声，由视频供应商原生人物声承载；不归属于人物的叙述旁白不进入视频模型人声，可选择独立 TTS 或外部后期配音；无人声单元不承载语音。模式从发声条目机械派生，不另存一个可编辑字段。
- **规划期直接形成同质单元**：机器候选混合人物发声与叙述旁白时进入带定位的隔离草稿，人工编辑时阻断提交。下游不自动切分、移动、删减或改写发声内容。
- **发声编排收口为深模块**：`SpeechComposition` 用输入适配器接收各内容骨架，准备阶段统一交付发声模式、问题，并按本次旁白交付方式交付条件化的 TTS 前置条件、实际时长下限与产物来源；呈现阶段以实际媒体交付机械字幕草稿和音轨放置。任务队列、项目迁移和供应商调用保留既有所有权，不吸入该模块。
- **叙述旁白的交付方式按请求选择**：一次视频生成请求显式选择“使用当前 TTS”或“后期配音”，不写入剧本、项目或独立确认状态。未配置 TTS 时只能选择后期配音，视频仍可生成；选择 TTS 时旁白必须先显式生成并可试听，当前 TTS 存在且未失效后点击生成视频即接受它。TTS 实际时长是视频申请时长下限，跨档重新确认时长与费用，超过最大档返回规划层；不截断、静默加速或跨单元泄漏。选择后期配音时按编排时长投影视频档位，不叠加旁白音轨，并导出旁白文字与机械字幕草稿。
- **批量准入全有或全无**：批量请求对全部目标使用同一旁白交付方式。选择 TTS 时，任一目标单元缺 TTS、TTS 生成中或失效、等待升档确认或超过时长上限都会使整批零任务入队；选择后期配音时这些 TTS 状态不构成 blocker。需要重新规划、参考请求不可执行等共同问题在两种方式下都阻断整批；问题按单元返回稳定 code、原因与下一步动作，Web 和智能体只做本地化或序列化。
- **首期不处理供应商原音**：原始视频与内嵌音轨保持不可变，不静音、不压低、不做语音分离或响度处理；只有选择 TTS 时才把它作为独立音轨直接叠加，后期配音方式不添加旁白音轨。没有 ASR 时只保证规划和请求不主动混合两类人声，不保证供应商实际波形绝无意外人物声。
- **字幕是机械草稿**：人物发声以实际视频总长为外边界；选择 TTS 的叙述旁白以实际 TTS 总长、后期配音的叙述旁白以实际视频总长为外边界；多条文本按规范化长度顺排，供人工调时，不宣称逐句对齐。
- **请求投影与可执行请求分时点**：费用、确认、入队身份与限流消费当前生成意图和本次旁白交付方式的请求投影；入队可近似锁定 provider/model，但不复制脚本文本、参考素材或完整请求，也不锁定编辑。任务执行开始时读取最新生成意图，一次物化请求参考集、真实能力桶、执行身份、申请时长、渲染提示、旁白交付方式与来源事实，此后本次运行不再变化。供应商提交后只持久化继续同一远端任务所需的提交检查点；完成时另记录各媒体自己的产物来源依据，恢复不按当前默认配置重建另一份请求。
- **产物按来源独立失效**：视频、TTS、字幕和最终呈现各自比较当前生成意图、旁白交付方式与产物来源。旁白变化只让实际依赖它的 TTS、字幕和呈现失效；视觉视频仅在选用 TTS 后实际时长跨越申请档位时失效，人物发声变化仍让视频失效。失效只改变匹配状态，绝不删除、清空或覆盖已有付费产物。
- **广告参考路线改用自包含单元**：`ad + reference_video` 退役运行时 `shots + reference_units` 双层真相，改用统一书写层 `video_units`。产品也使用 `@[名称]` mention，同名按 product → character → scene → prop 解析；参考单元不持久化 `section`，八段框架只作为生成提示。`ad + storyboard` 继续使用 `shots` 与 `section`。
- **旧结构只在启动时硬迁移**：已有分组保留顺序、边界、原样 `unit_id`、产物、版本、费用和任务身份；没有分组时按旧 shot 顺序一镜头一单元机械转换。旧时长之和成为编排时长，不按迁移时供应商档位量化。混合发声或悬空成员迁移成功但标记 `needs_replan`，保留内容和历史、阻止新生成；运行时不双读、不懒迁移，也不从磁盘残留文件猜测产物归属。

## 明确不采用

- **人物画外解说改走 TTS**：同一人物会在画内、内心与画外切换声音来源，违背声音一致性目标。
- **在执行期自动拆分混合单元**：用户不可见，破坏镜头连贯性与计费心智，并把规划错误扩散成下游状态机。
- **为单元增加内部持久时间轴**：首期没有可信时间来源，额外结构只会制造伪精确；字幕先以机械草稿交付。
- **让视频模型为 TTS 自动留白**：提示词不是可验证的音轨契约；在不静音原音且没有 ASR 时无法保证。
- **用 duck、静音或语音分离修复规划违约**：这些是后期策略，不能证明两类人声没有重叠；首期不额外处理原音。
- **强制叙述旁白先生成 TTS 才能生成视频**：TTS 是可选交付方式；没有配置或选择外部后期配音时，系统仍应按编排时长生成视频并交付旁白文字与字幕草稿。
- **把入队确认绑定不可变内容快照**：当前是单用户同项目操作，执行前采用最新生成意图更符合用户心智；执行开始后才冻结可执行请求。
- **删除失效产物**：媒体已经产生费用且大概率仍有价值，必须作为历史版本保留。
- **为广告旧结构保留运行时兼容**：会永久保留两套骨架、派生器和分支；一次性迁移后业务代码只认规范结构。
- **让一个全局可变聚合同时拥有规划、队列、迁移和媒体版本**：会把多个已有深模块吸成杂物袋并产生循环依赖；采用准备/呈现值接口与请求投影/可执行请求两个明确时点。

## 与既有 ADR 的关系

- 本 ADR **扩展 ADR-0010** 的可选 TTS 产物范围与生成基数：所有叙述旁白视频生成单元均可逐条生成 TTS，但视频请求也可选择外部后期配音；实际发起 TTS 时的队列调度、同步 backend 与无 provider resume 决定不变。
- 本 ADR **局部替代 ADR-0033** 的“广告剧本骨架不随生成路线变化”决定：仅 `ad + reference_video` 改用 `video_units`；`ad + storyboard` 的 `shots` 骨架和第三内容类型定位不变。
- 本 ADR **局部替代 ADR-0040** 关于同一单元允许交错两类发声、utterance 判别、发声归属与字幕时序的决定：一个视频生成单元只允许一种发声归属；人物内心独白和人物画外解说与人物对白同属人物发声，叙述旁白可选择 TTS 或外部后期配音；字幕按对应实际媒体外边界机械顺排。单一发声归属内的有序 utterances、`source_text` 与单向时长约束继续有效。
- 本 ADR 继续遵守 ADR-0049 的单次执行身份解析、ADR-0054 的声明近似与实际能力桶分流，以及 ADR-0056 的执行期判据与真实请求同源。

## Consequences

- `SpeechComposition` 的准备与呈现接口，以及参考单元请求规划的请求投影与可执行请求接口，成为主要行为测试面；各内容骨架、Web、智能体、费用、队列、供应商和剪辑出口只保留适配器契约测试。
- 说书、剧集和广告的规划提示、编辑器与校验器必须共同执行单一发声归属；只在某条执行路径过滤 voiceover 不再算满足约束。
- TTS 从“仅说书分镜路线的可选产物”扩展为所有叙述旁白单元均可选用的交付方式，但不成为视频生成的强制前置依赖；人物发声仍使用视频原音。
- 广告参考路线需要显式项目 schema 迁移、脚本级备份与原子提交；标准旧形态不得走迁移异常兜底。
- 泛化的项目迁移失败策略不变：异常项目记错后服务继续启动；`needs_replan` 是成功迁移后的业务状态，不是失败隔离。
- 实施顺序为：先建立窄版发声编排基础与统一问题模型，再迁移广告参考单元，随后收口可选 TTS / 后期配音交付、参考请求规划、字幕、费用、导出与各入口适配。
