# Never regenerate orphan tasks after restart; resume submit/poll backends by job_id

Previously, `generation_worker.py` called `requeue_running_tasks()` after obtaining leases with no local in-flight tasks, returning all orphan `status='running'` rows to queued for reclaim (no corresponding asyncio.Task in worker memory; the only real cause is service restart after deployment/crash). Reasonable for reentrant, duration-billed services, this is wrong for ArcReel: generation bills by **provider API call count**, so every requeue charges again. Individual videos cost fractions to several yuan, and deployment/OOM restart spikes can replay dozens. In a real 2026-05-24 incident, three long-polling Sora tasks filled custom-11's video pool of capacity 3; a then-existing inability to interrupt running asyncio.Tasks on cancellation deadlocked the project (current cancellation policy: `docs/adr/0006-cancel-only-queued-tasks.md`). Restarting would have charged all three again.

Orphans **never automatically trigger generation again**. Default to `failed` with "interrupted by service restart," leaving resubmission to users. For **submit/poll video backends** (such as Gemini/Ark/OpenAI/NewAPI, submitting once then polling job_id), provide polling resumption: add Task `provider_job_id` through alembic; persist IDs immediately after submit; startup calls new `resume_video(job_id)` for handled orphans without resubmitting. Missing IDs (synchronous backends or death before submit), unsupported resume, and expired/unknown jobs fail with `[restart_lost]` / `[resume_unsupported]` / `[resume_expired]` (family shorthand used here/comments; actual error_message uses structured `encode_failure` variants such as `restart_lost_image` / `resume_unsupported_provider` / `resume_expired_detail`, see `lib/generation/task_failure.py`). Vidu video also submits/polls, but polling is inline in `generate`, with no independent polling entry, and `generate` does not persist job_id, so cannot resume. Its orphans take missing-ID `[restart_lost]` (`restart_lost_no_job_id` / `restart_lost_checkpoint_no_job_id`), not `[resume_unsupported]`; `resume_unsupported_provider` guards only job_id + checkpoint with unsupported providers (`NON_RESUMABLE_VIDEO_PROVIDERS`, defending against configuration drift). **Images are outside resume scope**: most are synchronous request/response and lost on disconnect; even technically poll-based Vidu/NewAPI images are short enough that resume is not worthwhile under YAGNI. All image orphans fail for manual resubmission.

## Consequences

- Remove worker-loop `requeue_running_tasks()` calls, retaining the function only for tests/future manual rescue. Startup `_handle_orphan_tasks_on_start()` resumes eligible polling and fails others.
- Backends must cooperate: add optional `async def resume_video(job_id: str) -> ...` to `VideoBackend`, defaulting to `NotImplementedError`. Reuse existing `_poll_until_complete`, invoking by job_id directly instead of after submit without rewriting polling. Synchronous Grok image/video, Gemini/Ark/OpenAI images, and Vidu video with polling inline in `generate` and no persisted job_id do not resume; orphans fail (Vidu missing IDs use `[restart_lost]`).
- Users see most polling videos continue transparently after restart; most synchronous images fail and require existing generate-button resubmission. No retry UI in this confirmed scope: a conscious tradeoff keeping the PR to three queue-deadlock fixes.
- This relies on GenerationWorker staying attached to the server main process (module docstring `lib/generation/generation_worker.py`): one uvicorn process makes restarts the only orphan cause, without multiworker lease/heartbeat jitter creating false orphans while tasks still run. Future multiworkers require reassessment distinguishing newly started process orphans from tasks alive in other processes; reserve no such future logic now.
- Scan only `running`. Queued-only cancellation (`docs/adr/0006-cancel-only-queued-tasks.md`) removed `cancelling`; upgrade migrations convert leftover `cancelling` rows to `cancelled`, with no orphan branch.
- Independent of and consistent with `docs/adr/0006-cancel-only-queued-tasks.md`: 0006 governs user-cancellable tasks (queued only), 0007 handles unfinished work after restart. Orphans fail/resume, never become `cancelled`: cancellation is user intent, restart a system event.
- Never restore requeue for "more seamless restarts": it multiplies call-based charges by restarts and defeats this ADR's cost protection.
- Persist `provider_job_id` **synchronously before polling**. If `submit` returns IDs but database writes fail (SQLite I/O, disconnect), immediately mark tasks `failed` **without polling**, or providers continue charging while ArcReel cannot resume/cancel untracked ghost tasks. Commit job_id in a separate transaction after `submit`; failures raise immediately and worker finally marks failed; only successful commits enter `_poll_until_complete`.
- Fail-fast must be **observable**: structured logs for `provider_job_id` persistence failures start with stable `provider_job_id_persist_failed`, including task_id/provider/returned job_id/cause, letting operators distinguish ghost-task prevention from ordinary failures. This avoids silently hiding deployment regressions such as intermittent database I/O. Without existing prometheus/statsd/otel infrastructure, add no dedicated metric.
- Neither video route's resumable identity can rely on job_id alone. Immediately before first submit, persist dedicated versioned, strictly validated execution checkpoints and actual providers in one transaction. Freeze task/project/script/unit coordinates, buckets, provider/model/backend, custom-endpoint protocol, final prompts/durations/settings, and actual provider-media logical identities/digests/controlled locations. Do not rewrite enqueue payloads or mix facts with status, IDs, or Artifact Manifest current pointers; same-tier reuse never crosses submit boundaries or creates checkpoints.
- Exhaustively branch all video orphans by checkpoint/job combinations: neither means interruption before resumable submission; checkpoint only means attempted submission without poll handles, never resumable; both resume only with strictly parsed/bound checkpoints; jobs with absent/corrupt/mismatched-coordinate checkpoints are unrecoverable identities. Replay only checkpoint requests; current projects supply credentials/construction of identical backends. Provider/model/backend/custom-endpoint drift fails explicitly.
- Before submit, materialize actually attached first/last frames, references, and voice references into task-local immutable staging; providers read only those bytes. Enforce project boundaries, digest verification, atomic publication, and idempotent conflict checks. Failure/cancellation/terminal cleanup touches only task provider-media directories, never follows symlink/junction or deletes registered paid histories.
- Reference-payload 413 permits downgrade retries only when local evidence proves providers have not accepted requests. After persisted job handles or entering black-box calls where preacceptance rejection cannot be distinguished from postacceptance failure, propagate every 413 without automatic resubmission.
- Normal generation/resume share formal-file/version-registration transactions: providers write sibling temporary files, promoted only after download, accounting, and registration complete. Histories carry identical checkpoint provenance and standard visual bases, recording how paid requests arose without claiming continued consistency with current scripts/assets.
