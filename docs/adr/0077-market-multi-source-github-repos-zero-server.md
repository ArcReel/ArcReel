# 市场采用多市场源 GitHub 仓库，零服务端、零账号

自定义调用端点的分享此前止于文件导出与导入（#2128），「在线模板库 / 一键安装 / 社区分享平台」在 #2119 被列为范围外，原因是任何形态的中心 registry 都要 ArcReel 方运营服务端与账号体系。我们决定**市场以多个市场源承载，每个市场源就是一个 GitHub 仓库（或等价的直链地址）**：官方市场源 `ArcReel/arcreel-market` 随版预置、可禁用不可删除，同时是 GitHub 模板仓，fork 即第三方市场源；用户可添加任意合规仓库，添加时提示一次、信任自担；投稿 = 向官方仓提 PR，靠人工 merge 与 CI 校验把关。浏览与安装在开源版内完成；投稿在 GitHub 上完成，应用内只提供现有导出与指向官方仓投稿指引的链接，不接 GitHub 登录。「零服务端」指不设任何由 ArcReel 方运营的中心服务：本地 `server/` 照常承担 `/market` API、索引缓存与安装事务，抓取由后端发起而非浏览器直连。市场是用户功能：内嵌 Agent 不浏览、不安装市场条目，`/market` HTTP API 只服务前端。

**明确不采用**：① **服务端 registry 或站内发布**——要长期运营基础设施与账号，且与开源自部署的定位相悖。② **同一实例内用户间分享、链接 / 短码分享**——都需要一个可寻址的中心。③ **安装量、评分、评论等统计**——零服务端下没有数据源（raw 文件不计数，Obsidian 的下载量来自 Release 附件）；若将来要做，最简形态是 MoviePilot 式匿名计数服务，作为独立于索引的覆盖层另起，本 ADR 的设计不挡它。④ **主动下架提醒与远程禁用**——只能做被动状态（已安装端点在索引中消失即标「市场中不可用」）。

## 抓取全链路只经 raw 文件地址，不调用 GitHub API

索引、端点定义与 icon 一律按 `raw.githubusercontent.com`（或直链）抓取，全链路不打 `api.github.com`。GitHub API 匿名限流每小时 60 次，多源多用户下必然触顶，而放 token 又回到账号问题；更关键的是大陆可达性方案依赖这一约束——全局设置一项可空的代理前缀，对所有 raw 地址做前缀拼接，前缀能覆盖全部流量正因为只有 raw 一种地址（MoviePilot 的「API 不走镜像」缺口就是反例）。代价是拿不到 stars、Release、目录列表等 API 才有的元数据，索引须自带一切客户端要展示的字段；地址形态默认 ref 为 `HEAD`：raw 接受 `HEAD` 作为 ref 并解析到仓库默认分支，这是不打 API 也不写死分支名的唯一办法。

## 索引是定义 `meta` 的 CI 投影，由 bot 提交进仓

每个市场源发布一份 `arcreel-market.json`：浏览与刷新只读索引、不枚举目录；安装时才按条目的 `path` 抓取那一份定义，比对它与索引条目一致、过校验器后落库。索引不是手写的第二真相：**在生成索引的仓库（官方仓及其 fork）里，端点定义的 `meta` 是条目元数据唯一手写来源**，索引条目 = 生成器按目录约定写定的结构字段（`type`、目录名即 `slug`、`path`、`media_type`）+ `meta` 投影（名称、作者、版本、描述、主页、兼容门槛）+ 生成器发现的旁置资产（icon），由官方仓 CI 在 merge 后生成并以 bot commit 提交；结构字段没有手写来源，投稿者决定的只有目录名。为此定义 schema 升到 1.1.0，`meta` 新增可选 `min_app_version`（semver）：它由投稿者写在定义里、随 `meta` 投影进索引，市场功能随这一版 schema 一起发布，因此不存在「客户端认得索引里的门槛却读不了定义」的一代。投稿者只加自己的条目目录（`endpoints/<slug>/definition.json`），不碰索引，因此无 PR 合并冲突；不用生成器的第三方市场源可手写索引，客户端只要求它符合 schema。无论索引怎么来，与定义不一致时客户端拒装并提示，不默默以任一方为准；未知 `type` 静默忽略，为提示词 / 风格模板留位。索引不放多语言、tags、载荷 sha256——五家参照实现都没有，且加字段等于让索引脱离投影。

## 校验与生成器单一宿主在主仓，市场仓 CI 跟随 `@main`

索引校验规则与生成器只在本仓 `lib/market/` 实现一份，官方仓与 fork 的 CI 各只有两行 `uses:` 调本仓的可复用 workflow 并跟随 `@main`。一个数据仓的 CI 依赖应用仓主分支，将来的读者会问为什么：备选是把校验脚本复制进模板仓（fork 拿到的是 fork 时刻的快照，规则一变全部 fork 失联）或钉版本（每个 fork 要自己升级）。选跟随 `@main`，是用「主仓改规则可能让市场仓 CI 突然变红」换「规则只有一份实现、fork 零维护」；客户端刷新与安装本就用同一套校验器，规则分叉的代价比 CI 偶尔变红大。这不等于所有客户端与市场仓时刻同版：已发布的客户端带的是自己那一版校验器（定义 schema 顶层不接受未知字段），官方仓 CI 跟随 `@main` 因而可能接受旧客户端拒绝的定义——这是有意的，官方仓允许先于发版收录。偏差由条目的 `min_app_version` 承接：用了比某发布版更新的字段的条目须声明它，旧客户端列表照显、标「需要 ArcReel ≥ x.y.z」、安装禁用；索引主版本更高则整份拒读并提示升级。

## Consequences

- 新增市场源表与安装记录表，索引缓存落 DB（重启可浏览、离线看上次快照、多 worker 一致）；安装记录的设计见 `docs/adr/0078`。
- 官方仓默认分支即发布分支；下架 = 删目录不留痕，无 CHANGELOG / Release。
- 后续若要为市场引入任何服务端能力（统计、推送、远程禁用），须先修订本 ADR 的零服务端边界。
- 若要改走 GitHub API（搜索、stars、Release 资产），须同时重做代理前缀方案。
