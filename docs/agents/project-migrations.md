# Project Schema Migrations

新增或修改 `lib/project/project_migrations/` 里的一步迁移，或改动产物补录规划器（`lib/artifacts/artifact_planner.py`）时按此文档工作。迁移链的结构、备份命名与失败裁决的机制见 `docs/adr/0022`、`docs/adr/0062`、`docs/adr/0075`；本文档只放代码里查不到的约定。

## 步骤

1. **列出这一步要处理的全部旧形态。** 每种形态是「某个版本之前的代码写出的、与当前代码期望不同的数据」；下表是已知清单，新发现的形态先补进表里。完成判据：每种相关形态在 `tests/legacy_project_shapes.py` 里有一个构造出的样本。
2. **写迁移器，登记与跳过都要有出口。** 一个发行版至多新增一步迁移：`CURRENT_PROJECT_SCHEMA_VERSION` 比最近的 `v*` 发版 tag 上的值大，说明最新一步尚未发版，改动并进这一步；两者相等才新开一步。改写产物清单的迁移返回 `ArtifactBackfillOutcome`（`lib/project/project_migration_report.py`），runner 把它折进项目内的 `.migration_report.json`。规划器里每一条「不登记」的分支调用 `_skip(...)` 给出原因，用户该看到的再带上 `category`：`unreadable`（产物文件读不出）或 `legacy_audio_basis`（旧版配音缺 TTS 设置）。不带 `category` 的跳过是依据算不出，读时报 missing，不进报告。完成判据：每一条带 `category` 的跳过都出现在迁移报告里。
3. **在旧形态样本上跑到用户口径。** 除迁移器本身的断言外，至少一条用例用 `WorkflowStateService.get_project_summary` / `get_status` 或演示读模型断言用户看到的结果（计数、状态、预览可用）。完成判据：`tests/integration/lib/project/project_migrations/` 下的用例覆盖了「≤ 上一版实际安装」到当前版本的整条链（`migrate_project_dir`），不只单步。
4. **同步面向用户的迁移说明。** `website/docs/ops/deployment.md` 的「项目结构迁移」一节描述备份、报告与重试行为；行为变了就改它。

## 约定

- 升级路径常常跨多个版本：迁移要处理的是更早版本留下的全部变体，不只上一版写出的标准形态。
- 备份走 `lib/project/project_migrations/backups.py`；自行备份输入的迁移器登记到 runner 的 `_MIGRATORS_WITH_OWNED_BACKUP`。
- 改写清单的迁移用 `activate_artifact_target_state(bump_schema=True, target_schema_version=...)`，先做只读预检再落盘。
- 整份激活会把在场产物一律登记为时新。改的只是某个依据输入、既有产物本不该因此过期时，改前改后各规划一次目标态，只把「改前正是时新、且目标登记变了」的条目改写过去（先例：v13→v14 的风格值归一），本就过期的条目不被伪造成时新。带信封的归档导入在迁移前把信封里的 claim 落成暂存清单（`stage_preserved_artifact_claims`），迁移链像原地升级一样改写它们，改写清单的迁移步不必为归档另写路径；导入激活再按内容证据恢复迁移后的 claim。
- 过去正常流程写出的旧形态在链首统一规整：`legacy_shapes.normalize_legacy_shapes` 在链上第一个 ≥ v6 的版本跑一次，先于 v6→v7 的剧本改写与任何一次目标态规划，之后的迁移步与规划器只见规整后的形态。新发现的这类形态加到这里，不在各步里各自拒绝。因数据拒绝整个项目只限 `project.json` 或剧本读不出、`versions.json` 或 `.arcreel_artifacts.json` 读不出、剧本条目结构损坏（v6 广告旧镜头索引或单元结构损坏、v8 单元不是对象）与导入包不安全；规划器的容错只在激活模式（`_activation_mode`）下生效，运行期行为不变。
- 规整的每处改动记成 `MigrationAdjustment`（报告「已调整」），读不出而原样留下的文件记成带 `category` 的跳过（报告「未能带入」）；报告只有这两栏。依据算不出（生成缺口、没有版本记录、路径不规范、源文不是 UTF-8 等）的跳过不带 `category`，由 `write_migration_report` / `extend_migration_report` 滤掉；需要重新规划的单位也不进报告：带 `needs_replan` 的条目，其分镜图、视频与配音由 `write_migration_report` 统一从「未能带入」里去掉，不靠各条跳过路径各自记得。归档导入不分 schema 版本，把导入激活没能登记的产物与修复期补的占位一并并进报告（`extend_migration_report`）。链中途失败时，已做的调整写进一份 `complete: false` 的报告，重试时并入下一次报告；未完成的报告不对用户显示。链在提交当前版本之后才失败（最后一步提交后报错，或收尾那次写报告失败）时重试不再进链，runner 见到项目已在当前版本、报告仍未完成，就把它补写成完成的报告。
- 有取舍时被替下的那份用 `backups.set_aside_as_kept_copy` 留作保留副本（`<name>.kept.v<N>-<ts>`），不被 `cleanup_stale_backups` 清理，路径写进调整条目的 `backup`；只是改写的文件照常做版本化备份。
- 生成缺口不等于「投影不出来」：缺口只拦生成，期望依据照常由已有的输入值构造，缺的项记在依据的 `absent` 里（`lib/artifacts/input_gap.py`）；没有缺口时依据不写这个键，输入完整的已登记条目摘要不变。schema < 18 的项目按「有缺口即投影不出」的口径规划，v17→v18 之前各步的激活与来源补写不受影响。
- 依据确实算不出的目标不登记，读时报 missing；这不等于「不存在」，也不等于「整项目失败」。其中只有文件读不出（规划器 `artifact_unreadable` 阻断）进报告，其余不进。归档导入只在报告非空时要求确认，当前代码导出的健康项目再导入不弹确认、不留报告。
- 规划口径放宽、原先跳过的产物现在能登记时，改前改后各规划一次，只补「改前没有目标、改后有、清单里也没有」的条目，已登记条目一律不动（先例：v17→v18 的缺口补录，`lib/project/project_migrations/input_gap_backfill.py`）。带信封的归档导入按同一差集补录信封里没有 claim 的产物。
- 迁移不推进项目的最近活动时间：`project.json` 与剧本的 `metadata.updated_at` 保留原值，新写出的剧本不以迁移运行的时刻作为 `updated_at`；不调用 `lib.project.project_activity.record_project_activity`，也不经过调用它的业务写入出口（草稿、正式脚本规划写盘事务、剪辑时间线存储、项目记忆）。
