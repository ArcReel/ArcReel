# 教训的记录与晋升

[`docs/LESSONS.md`](../LESSONS.md) 是环境改进的候选池：agent 出过、而现有规范和检查都没拦住的错先记在这里，同类问题重复到阈值再晋升。台账收录所有环境问题，编码与流程问题都算在内；记录时不预判去向。

台账在实现与审查阶段都不读。唯一写入者是 [`lessons-sweep`](../../.agents/skills/lessons-sweep/SKILL.md) 巡检；用户手动运行 `/retro` 时也可以直接修改。其余 agent 只经下面的收尾自查提交候选。

## 收尾自查

凡最终要提 PR 的工作都在收尾时自查一次，包括交互式会话和小修复；AFK 批次中的 implementer、stage-reviewer、review-looper 各自查一次。

自问：这次有没有出过错，而且现有规范和检查都没拦住？

- **出过错**：被采纳并修复的审查意见、推翻已写代码的返工、CI 暴露的逻辑错误、合并后修复或 revert。
- **没拦住**：lint、类型检查、测试与 audit 脚本都没报出它，审查也没有引用现有规范指出它。只凭 reviewer 自身判断发现的，以及审查之后（合并后修复、revert、main CI 失败）才暴露的都算。

有这类错时，在 PR 创建后于该 PR 上发一条评论：首行是 `<!-- lesson-candidate -->`，其后按[条目格式](#条目格式)写一个条目，出现记录在漏因前补上 `根因：<…>`。同一 PR 上已发过的候选不再重复发。

问题出在更早的 PR 里时，评论仍发在当前 PR，编号按「计数与晋升」的计数单位写。

以下情况不算教训：被驳回的审查意见、纯措辞修改、一次就修好的常规检查失败。

AFK 角色还没有自己的 PR 时（implementer，以及 stage PR 创建前的 stage-reviewer），把候选按同一格式写进 handoff，由 team-lead 在 stage PR 上统一发评论。

## 条目格式

```markdown
### <一句话规则，正面表述>
模式：<在什么情况下会犯，表现是什么>
代价：<后果>（严重度：常规 / 数据·安全·计费）
可判性：机械（拟用 <工具>）/ 需要判断
- #3101 · 2026-10-13 · 审查发现：<一句现象>；漏因：<为什么没拦住>
- #3139 · 2026-10-14 · 合并后修复：<一句现象>；漏因：<…>
```

- 出现次数与最后出现日期从出现记录统计，不另设字段。
- 来源写发现途径，例如自查、审查发现、合并后修复、revert、main CI 失败。
- 漏因取三者之一：没有对应规则；有规则但没被执行；检查没接上。

## 分组

- 按失败模式分组。按代码位置分组会把同一模式拆到几处，计数永远凑不够阈值。
- 组用二级标题，条目用三级标题。不预设分类表：条目归入最接近的组；归不进的先放在「未分组」，累积到两条以上同类条目时新建组；组可以合并、拆分。
- 文末的「已晋升」区记录移走的条目，写明去向并保留出现记录。

## 信息边界

本仓库公开。条目只写技术事实（PR 与 commit 号、现象），客户、渠道与商业信息不进台账；涉及私有实现的教训不写进本仓库。

## 计数与晋升

- **计数单位**：不同的 PR 或 issue。同一 PR 内反复出现只算 1 次。一起事故只记一条出现记录，编号写引入问题的 PR，找不到时写发现问题的 PR；从多个来源收集到同一起事故时合并成一条，修复 PR 号可附在现象里作证据。
- **晋升阈值**：机械可判的满 2 次做成检查；需要判断的满 3 次写成规则；严重度为数据·安全·计费的出现 1 次就进入晋升评审。
- **去向**：可以是检查、规范、skill、导航指针或架构文档，按 [`CODING_STANDARDS.md`](../../CODING_STANDARDS.md)「维护」的判据裁决；未通过准入判据的留在台账继续计数，并追加一行 `评审未晋升 · <日期> · <一行理由>`（不计入出现次数）；这行之后出现新记录才重新评审。跨领域的模式写进 `docs/standards/general.md`。
- **过期**：最后一次出现超过 90 天的条目删除，git 历史即归档。注有 open issue 号的条目与「已晋升」区不过期。

## 规范退出

- 规则已做成检查，或那类错误在架构上已不可能发生：删除规则。
- 规则存在满 90 天、且最近 90 天合并的 PR 中没有被审查评论引用过，是删除候选，用准入判据中的反事实检验裁决。这 90 天须整段落在台账首个 reviewed-through（`486a901`，2026-10-19）之后；每次巡检最多裁决 5 条，近 90 天巡检 PR 中已裁定保留的跳过。
- 有事故来源的规则降级回台账：附上「已晋升」区中的已知出现记录，再追加一条 `降级 · <日期> · 自 <规范文件 + 规则标题>`，过期从这条记录起算；重新晋升只计这条记录之后的出现，之前的记录只作背景。
